## 0. 왜 바꾸는가

사용자 질문은 "벽면 착탄점이 유사한 패스가 이 정도로 없어? 차이가 좀 많이 나는 것 같아서."였다.
직전 워크플로가 답한 것(재조사하지 않는다):

- 비슷한 패스는 **있다.** 착탄 중점 15 cm·방향 ±30° 이웃이 패스당 중앙값 10개다.
- 그런데 화면이 먼저 보여 주는 기준은 그 이웃이 아니다. `/api/reference`의 `candidates` 목록은 **세션 파일 순서 × 패스 순번**으로 서고,
  화면(`static/app.js`)은 `candidates[referenceState.index]`의 초기값 `index=0`, 곧 **첫 항목**을 보여 준다. 착탄 위치와 무관하다.
- 실측(`docs/measurements/2026-09-22-same-level-pairs-d1-prereg.md` R6): 사용자 화면 패스 **김경호 L1 1000389_1 #0**은 m3 키에서 후보가 9개인데
  자동 기준(1000564_1 #15)까지 착탄 중점 거리가 **0.360 m**다. 같은 55패스에서 후보 전체의 거리 중앙값은 0.195 m였다.
  곧 더 가까운 후보가 목록 안에 있는데도 화면이 먼 것을 먼저 골랐다.

**사용자 결정: 후보를 질의와의 착탄 중점 거리 순으로 정렬해 가장 가까운 것을 먼저 보여준다.**
화면이 고르는 기준이 바뀌므로 개선율 연구의 쌍 규칙도 같은 규칙으로 바꾸고, 현 기준선 N·m3 위에서 판정한다.
이 변경을 **P1**이라 부른다.

## 1. 선택 규칙의 정의

### 1.1 "착탄 중점 거리"의 정의

**점.** 패스 하나의 착탄 중점은 `service.KeyInputs.hit`이다. 곧 `stroke_frame.resample_frames(raw_frames, samples=20)`이 만든
리샘플 격자의 가운데 점 `frames[len(frames) // 2]`(20점이면 색인 10, 정규 호장 s = 10/19 ≈ 0.526)의 `hit`이고,
그 점에 `hit`이 없으면 `frames[0].hit`이다(`service.key_inputs`, `service.py` 194·203행).

- 이것은 **동작 키의 `hit` 성분과 같은 점**이다. 키가 "어디를 칠했는가"로 쓰는 점을 정렬에도 그대로 쓴다.
- 이것은 **m3 키의 UV 칸을 고른 점과는 다르다.** m3의 칸은 `motion_key.midpoint_uv`가 고른 **원 프레임** 호장 중점(s ≈ 0.5)의 UV다.
  격자 중점(s ≈ 0.526)과 원 프레임 호장 중점(s ≈ 0.5)은 서로 다른 프레임일 수 있다. 이 비대칭은 D1 사전등록 §3.1이 의도적으로 남긴 것이고,
  P1은 그것을 건드리지 않는다. 원 프레임 호장 중점의 `hit`을 쓴 변형(`nearest_raw`)은 §3.6의 **보고 전용** 변형으로만 낸다.
- 이 점을 고른 실무적 이유도 적는다. `csv_source.PassIndexEntry`는 `key_inputs`를 이미 들고 있다(`csv_source.py` 72–78행).
  그래서 후보의 `hit`은 CSV를 다시 읽지 않고 얻는다. 원 프레임 호장 중점의 `hit`은 색인에 없어 후보마다 CSV를 다시 읽어야 한다.

**거리.** 질의의 `hit`과 후보의 `hit` 사이의 **3차원 유클리드 거리**(`math.dist`), 단위 m.

**좌표.** CSV 월드 좌표 그대로다. 이 월드는 **유니티 Y-up**이다(수직축은 Y이고 Z가 아니다).
축 이름을 코드나 문구에 새로 쓰지 않는다 — 거리는 세 축을 대칭으로 쓰므로 축 이름에 의존하지 않는다.
**레벨 좌표로 투영하지 않고, 어떤 축도 가중하지 않고, 바닥 높이를 빼지 않는다.** 후보 집합이 이미 같은 레벨이라(§2)
월드 거리는 같은 벽 위의 두 점 사이 거리다. 다른 레벨 사이의 거리는 P1에서 한 번도 계산되지 않는다.

**정렬 키와 동률.** 후보를 `(distance, date, session, pass_index)` 오름차순으로 정렬한다.
동률(부동소수점으로 정확히 같은 거리)이면 `(date, session, pass_index)`로 갈라진다 — HEAD가 목록을 세우던 바로 그 순서다.
그래서 정렬은 결정론이고, 같은 입력에 두 번 부르면 같은 순서가 나온다. 난수는 쓰지 않는다.

**거리를 못 구하는 후보.** 거리가 `None`이거나 유한하지 않은(`nan`/`inf`) 후보는 **목록의 맨 뒤**에 두고, 그들끼리는 `(date, session, pass_index)`로 세운다.
조용히 버리지 않는다 — 버리면 후보 집합이 바뀌고(§2를 어긴다) 화면의 "N개 중 k번째"가 틀린다.
현재 코드에서 이런 후보는 **0이어야 한다**: `csv_source._entry_for`는 `first.hit`/`last.hit`이 없는 패스를 색인에 올리지 않고(`csv_source.py` 286–287행),
`service.key_inputs`도 같은 조건에서 `None`을 내므로(`service.py` 192–193행) 색인에 오른 후보는 모두 `hit`을 갖는다.
질의 쪽도 `key_inputs`가 `None`이면 `reference_candidates`가 이미 `status="unavailable"`(`insufficient_frames`)을 낸다.
그래도 정책을 적어 두고, 실제 개수를 세어 보고한다(§6 F5).

### 1.2 규칙을 **한 곳에만** 쓴다

정렬은 `service.reference_candidates`가 `candidates` 목록을 만드는 **그 자리**에서 한다. 구현은 이 한 곳뿐이다.

- 화면(`/api/reference` → `static/app.js`)은 이미 서버가 준 순서 그대로 `candidates[0]`을 보여 준다. 화면 코드는 고치지 않아도 가장 가까운 것을 먼저 보게 된다.
- 연구(`improvement_study.select_pairs_screen`)는 같은 함수를 직접 부르고 그 목록의 `[0]`을 쓴다(`choose="first"`).
  연구 쪽에 거리 계산이나 정렬을 다시 쓰지 않는다. 두 번 쓰면 조용히 갈린다(이 프로젝트가 M0에서 이미 겪은 결함이다).
- 연구의 새 기본 쌍 규칙 이름은 **`P`**(`--pair-rule screen --choose first`)로 하고, 기존 `--choose random`(N)은 귀무 분포를 만드는 데만 쓴다.
  `--choose random`은 후보를 스스로 `(date, session, pass_index)`로 다시 정렬한 뒤 뽑으므로 **응답 순서와 무관하다**(`improvement_study.py` 425행).
  그래서 §3.3의 귀무 추첨 8회는 정렬이 들어오기 전에 돌리든 후에 돌리든 같은 값이어야 한다. 이것을 단언한다(§7 검사 6).

### 1.3 화면에 무엇을 더하고 더하지 않는가

- 응답(JSON)의 후보 행마다 `hit_distance_m`(질의와의 거리, m)을 싣는다. 연구와 검사와 사후 분석이 같은 수를 읽어야 하기 때문이다.
- **3D 화면에는 글자를 늘리지 않는다.** 거리를 화면에 표시하지 않는다. `static/app.js`가 이 필드를 렌더링하지 않는지 확인하고, 확인 방법을 결과에 적는다.
  기존 문구(`N개 중 k번째`, `[다른 기준 ▸]`)도 그대로 둔다.

## 2. 무엇이 바뀌고 무엇이 안 바뀌는가

**바뀌는 것은 `candidates` 목록의 순서 하나뿐이다.**

바뀌지 않는 것(하나라도 바뀌면 §6 F1·F2가 발생한 것이다):

| 항목 | 그대로 두는 값 |
|---|---|
| 기준 작업자 | 전형기 고정(`service.EXPERT_WORKER`) |
| 레벨 | 질의와 같은 레벨만(`source.passes(..., level=query.level, limit=50)`) |
| 자기 제외 | `PassRef` 다섯 성분이 모두 같은 패스만 뺀다 |
| 동작 키 사다리 | `uv8 → uv4 → uv2 → uv_off`, **후보가 하나라도 나온 첫 단**에서 멈춘다 |
| 세션 한도 | `limit=50`, `truncated` 보고 방식 |
| 리샘플 N | `samples=20` |
| 동작 키 | m3(`motion_key.KEY_PREFIX = "m3"`), 격자 `uv_size=2048`, 모든 문턱 |
| 산포 아티팩트 | `/output/spread_reference_expert_m3.json` |
| 채점 경로 | `service.compare(..., reference_spreads=..., include_view=False)` |
| split의 A/B 날짜 분리 | `exclude_dates`(질의가 전형기면 질의 날짜 제외) |
| 요약 | `summarize`, 문턱 0.70 |
| 질의 표본 | `--pairs 200 --seed 20260828`, `sample_queries`의 셔플 |
| 색인 캐시 지문 | `_fingerprint`의 `key_prefix` 필드 유지 |

특히 **후보 집합(멤버십)은 정렬 전후로 같은 집합이다.** `match_granularity`, `ladder`의 단별 건수, `sessions_scanned`, `sessions_total`, `truncated`,
`query_key`도 모두 같다. 정렬은 고른 뒤에 하는 일이지 고르는 일이 아니다.

## 3. 성공 기준

### 3.1 기준선

현 기준선은 **N·m3**이다(직전 사전등록 R3·R5, 커밋 `8ec2cf9`, 산출물 `/output/samelevel/study_N_m3.json`):

- `p_base` = split ≥0.70 비율 = **0.8210526315789474 (156/190)**
- `med_base` = split 중앙값 = **0.8369118180324692**
- `n_base` = **190**
- 조건: 쌍 규칙 N(`--choose random`), `--seed-ref 20260828`, 키 m3, 산포 `/output/spread_reference_expert_m3.json`.

### 3.2 왜 τ를 그대로 쓰지 않는가

직전 사전등록의 τ_p 3.1 %p·τ_med 0.014는 **m1 키** 위에서 기준 패스를 다시 뽑아(`seed_ref` 4개) 잰 잡음이었다.
P1의 상황은 둘이 다르다.

1. 키가 m3로 바뀌었다. 같은 잡음이 m3에서도 그 폭인지는 재지 않았다.
2. **P1은 결정론이다.** 기준선은 무작위 뽑기 한 번의 값이고 P1은 뽑기가 없는 값이다.
   "기준선 한 값 대 새 값 한 값"을 τ로 비교하면, 기준선이 우연히 높게/낮게 나온 몫이 판정에 통째로 들어간다.
   R2의 m1 귀무 재추첨에서 ≥0.70 비율은 80.00–84.21 %를 오갔다. 한 값끼리의 비교로 3 %p 미만을 가를 수 없다는 뜻이다.

그래서 **기준선 쪽을 여러 시드로 돌려 분포를 만들고, P1의 값이 그 분포 안인지 아래인지로 판정한다.** τ는 그 분포 위에서 m3로 다시 잰다.

### 3.3 귀무 분포 — 몇 개 시드를 쓰는지 미리 적는다

- 키 m3, 산포 `/output/spread_reference_expert_m3.json`, 질의 표본 동일(`--pairs 200 --seed 20260828`), 쌍 규칙 `--choose random`으로
  **`--seed-ref 20260829, 20260830, 20260831, 20260832, 20260833, 20260834, 20260835, 20260836`(8회)**를 돌린다.
  비용을 줄이려고 `--skip-sensitivity --skip-extras`를 쓴다. split 값은 extras와 무관하다(R2에서 확인된 사실).
- 이미 있는 기준선(`seed_ref = 20260828`)을 더해 **귀무 값 9개**가 된다. 산출물은 `/output/nearest/null_m3_{seed}.json`, 집계는 `/output/nearest/null_m3.json`.
- 판정 문턱:
  - `p_floor_dist` = `min_k p_null_k`(9개의 최솟값), `med_floor_dist` = `min_k med_null_k`.
  - **근거.** "P1이 개선율에 아무 영향이 없다"는 귀무 아래에서 P1의 값은 이 9개와 교환가능하다.
    그러면 P1이 9개 전부보다 낮을 확률은 1/10 = **10 %**다. 이 10 %를 한쪽 유의수준으로 받아들인다.
    시드 8개로 정한 이유가 이것이다. 4개(R2와 같은 수)면 1/5 = 20 %로 너무 헐겁고, 16개면 비용이 두 배인데 5.9 %로 조금 엄해질 뿐이다.
  - `τ_p` = `min(3.1 %p, max_k |Δp_k|)`(0.1 %p 단위 올림), `τ_med` = `min(0.014, max_k |Δmed_k|)`(0.001 단위 올림).
    `Δ`는 8개 새 추첨 각각에서 기준선(`seed_ref = 20260828`)을 뺀 값이다. 상한 3.1 %p·0.014는 직전 사전등록 §3.2가 부트스트랩으로 정한 값 그대로 쓴다
    (같은 표본 크기·같은 지표라 상한의 근거가 그대로 유효하다). **상한으로 잘렸으면 그 사실을 결과의 첫 줄에 적는다.**
- **확정 절차:** 귀무 8회를 먼저 돌리고 `p_floor_dist`·`med_floor_dist`·`τ_p`·`τ_med`·`Δn_k`를 이 문서 **R2에 적어 커밋한 뒤에** P1을 구현하고 잰다.
  P1의 값을 하나라도 본 뒤에 문턱을 고치지 않는다.

### 3.4 성공 기준 (모두 AND)

`C`를 "기준선(N·m3)과 P1 모두 split이 계산된 질의"의 공통 집합이라 하자.

- **(a) ≥0.70 비율, 전체**: `p_P1 ≥ max(p_floor_dist, p_base − τ_p)`
- **(b) 중앙값, 전체**: `med_P1 ≥ max(med_floor_dist, med_base − τ_med)`
- **(c) 공통 집합 C**: `p_P1(C) ≥ p_base(C) − τ_p` **그리고** `med_P1(C) ≥ med_base(C) − τ_med`.
  분모가 바뀌면서(어려운 질의가 빠지면서) 비율이 좋아 보이는 경우를 막는다. C에서는 귀무 분포를 다시 계산하지 않고 τ만 쓴다 — 9개 추첨마다 C가 달라 한 문턱으로 묶을 수 없다.
- **(d) n**: `n_P1 ≥ n_base − 4 = 186`. 줄어든 수와, 빠진·새로 생긴 질의 목록을 적는다.
  R2(m1)에서 `Δn_k = 0`이었으므로 m3에서도 0을 기대한다. 0이 아니면 그 값을 §6 F9로 보고한다.

(a)·(b)에서 두 문턱 중 **더 엄한 쪽**을 쓴다. 분포 문턱은 기준선 한 값이 우연히 높았을 때를 막고, τ 문턱은 귀무 추첨 9개가 우연히 다 높게 몰렸을 때를 막는다.
둘은 서로 다른 실패를 막으므로 함께 건다.

### 3.5 자기충족 대비 — "유사도가 올랐다"는 성공 근거가 아니다

가까운 기준을 고르면 **교정 전 유사도 자체가 올라간다.** 비슷한 패스끼리 비교하기 때문이다.
그러면 좁힐 여지(gap)가 줄어 `gap_closure`로 정의된 개선율은 **오히려 떨어질 수 있다.** 이것이 P1의 가장 큰 위험이다.

- **판정은 오직 개선율로 한다**(§3.4의 split ≥0.70 비율과 split 중앙값). 아래 표의 어느 값이 좋아지더라도 그것을 성공 근거로 쓰지 않는다.
- 다음을 쌍마다 기록하고 기준선과 나란히 보고한다. 무엇이 움직였는지 보이게 하기 위해서다(판정에 쓰지 않는다).

| 기록할 것 | 출처 |
|---|---|
| 교정 전 유사도(채점 레퍼런스 B 기준) | 쌍 기록의 `before_split_score` |
| 교정 전 유사도(F 레퍼런스 기준, same의 S0) | 쌍 기록의 `before_same_score` |
| 교정 후 유사도 | `before_split_score`와 `split`에서 복원(`after = before + split·(1 − before)`), 그리고 `score_after` |
| 개선율 same | 쌍 기록의 `same` |
| 짝 착탄 중점 거리 | §1.1의 거리. 중앙값·p90·≤0.15 m 비율·≤0.30 m 비율 |
| 짝 머리 수직값 차 | `|Δ head|`의 수직 성분, p90(직전 사전등록 R3의 "연구 쌍 머리 수직 차 p90"과 같은 정의·같은 스크립트) |
| 후보 수와 기준 단 분포 | `candidate_count`, `reference_granularity` |

- **미리 적는 예상과 그 뜻.** 짝 거리 중앙값은 내려가야 한다(안 내려가면 구현이 틀린 것이다, F7).
  교정 전 유사도는 **오를 것으로 예상한다.** 그것이 오르는데 split ≥0.70 비율이 문턱 아래로 떨어지면, 그것은 "성공했는데 지표가 못 따라온 것"이 아니라
  **자기충족이 실제로 개선율을 깎은 것**이다. 그 경우 §5에 따라 되돌린다.

### 3.6 보고 전용 변형 (판정에 쓰지 않는다)

- **`nearest_raw`**: 정렬 거리를 원 프레임 호장 중점(`motion_key.midpoint_uv`가 고른 프레임)의 `hit`으로 바꾼 것. §1.1의 비대칭이 실제로 얼마나 다른 짝을 만드는지 본다.

## 7. 성질 검사 — 각각 일부러 깨뜨려 실패를 본 뒤에만 인정한다

구현 단계에서 쓴다. 검사 이름과 단언문, 깨뜨린 방법과 그때 나온 실패 메시지를 결과에 인용한다.

1. **정렬은 순서만 바꾼다.** 실데이터 질의 여러 개에서, 정렬된 `candidates`의 `PassRef` 다중집합이 정렬 전의 것과 같고
   `match_granularity`·`ladder`·`truncated`·`sessions_scanned`·`query_key`도 같다. (F1·F2)
   - 깨뜨릴 방법: 정렬에서 거리 상위 k개만 남긴다 → 집합 불일치로 실패해야 한다.
2. **첫 후보가 가장 가깝다.** 모든 질의에서 `candidates[0]["hit_distance_m"] == min(모든 후보의 거리)`이고,
   목록의 거리 수열이 비내림차순이다. (F4)
   - 깨뜨릴 방법: 정렬을 내림차순으로 바꾼다.
3. **동률과 결정론.** 거리가 정확히 같은 후보를 둔 페이크 소스에서 `(date, session, pass_index)` 순으로 서고, 같은 호출을 두 번 하면 순서가 비트 단위로 같다.
   - 깨뜨릴 방법: 정렬 키에서 동률 갈래를 빼고 `key=distance`만 남긴 뒤, 입력 순서를 뒤집어 넣는다.
4. **거리 없는 후보는 맨 뒤.** `hit`이 없는 후보를 가진 페이크 소스에서 그 후보가 목록에 남아 있고 위치가 맨 뒤다. (F5)
   - 깨뜨릴 방법: 거리 없는 후보를 거른다 → 후보 수 불일치로 실패해야 한다.
5. **화면과 연구가 같은 패스를 고른다.** 실데이터 질의 여러 개에서 `/api/reference`를 TestClient로 부른 `candidates[0]`과
   `select_pairs_screen(..., choose="first")`의 기준이 같다. skip 없이 실패할 수 있어야 한다. (F12)
   - 깨뜨릴 방법: 연구 쪽에서만 후보를 `(date, session, pass_index)`로 다시 정렬한다.
6. **`--choose random`은 응답 순서와 무관하다.** 후보 목록을 뒤집어 주는 가짜 `candidates_fn`을 넣어도 `choose="random"`의 쌍이 그대로다. (F6)
   - 깨뜨릴 방법: `select_pairs_screen`의 `sorted(refs, ...)`를 지우고 `refs`를 그대로 쓴다.
7. **거리의 정의가 R6과 같다.** 김경호 L1 1000389_1 #0에 대해, 정렬 전 자동 기준(1000564_1 #15)까지의 §1.1 거리가 0.360 m를 재현한다(소수 셋째 자리). (F13)
   - 깨뜨릴 방법: 거리를 수평 2차원(수직 성분 제외)으로 바꾼다.
8. **화면 문구가 늘지 않았다.** `static/app.js`에 `hit_distance_m`을 그리는 곳이 없다. (F14)
   - 깨뜨릴 방법: 후보 문구에 거리를 덧붙인다.

## 8. 함께 고칠 것 — `build_spread_reference`의 키 UV 경로를 지키는 회귀 검사

직전 검증자가 남긴 구멍: **`build_spread_reference`의 키 UV 경로만 첫 프레임 UV로 되돌려도 전체 스위트가 통과한다.**
곧 D1(m3)의 세 적용 지점 중 산포 빌더 하나가 검사 없이 서 있다. 되돌아가면 산포 버킷이 시작점 칸으로 매겨지고,
화면은 m3 키로 후보를 고르면서 채점만 m1 칸의 산포로 하게 된다 — 조용히.

- **넣을 검사**: 시작 칸과 호장 중점 칸이 서로 다른 uv8 칸에 드는 패스를 포함한 입력에서,
  `build_spread_reference`가 만든 버킷 키가 `service.pass_key_inputs` → `service.key_from`으로 만든 키와 같다고 단언한다.
  시작 칸으로 매긴 키와는 **다르다**는 것도 같은 검사에서 단언한다(두 칸이 같은 입력이면 검사가 아무것도 지키지 못하므로).
- **일부러 깨뜨릴 방법**: `build_spread_reference`의 키 재료 호출을 `key_inputs(frames, raw_frames=frames)`로 바꾼다.
  `raw_frames`가 키워드 필수라 이름을 빼면 `TypeError`가 나지만, 리샘플 격자를 원 프레임 자리에 넣으면 **조용히 첫 프레임 UV**가 된다. 이것이 정확히 그 구멍이다.
  이 상태에서 새 검사가 실패하는 것을 보고, 실패 메시지를 결과에 인용한 뒤 원상 복구한다.
- 검사가 실패하지 않으면(§6 F16) 그 검사는 아무것도 지키지 않는 것이므로 검사부터 다시 쓴다.
- **F16.** 위 되돌림을 넣었는데 새 검사가 통과한다. → 검사가 실패할 수 없는 단언이다. 이 프로젝트의 반복 결함이므로 검사를 다시 쓴다.

새 기준선은 P1의 값이다: **split ≥0.70 = 82.63 %(157/190), 중앙값 0.8400303737444659, n 190**(전문가 대 전문가 한정).

**화면 영향**(출처 `/output/nearest/screen_impact_p1.json`, 스크립트 `/output/nearest/screen_impact_p1.py`).
사용자 화면 세션 두 개(김경호 L1 1000389_1, L3 1000391_1)의 55패스, 그중 후보가 있는 51패스:

- **사용자 화면 패스 김경호 L1 1000389_1 #0: 자동 기준도 거리도 바뀌지 않는다.** 여전히 전형기 1000564_1 #15이고 0.360 m다.
  이유가 이번 측정의 직접적인 답이다 — 이 패스의 후보 9개의 거리가 **0.360 · 0.365 · 0.365 · 0.365 · 0.371 · 0.374 · 0.384 · 0.388 · 0.407 m**로,
  정렬 전 첫 후보가 이미 가장 가까웠다. 곧 이 패스에 한해서는 "더 가까운 후보가 목록 안에 있는데 먼 것을 먼저 보여 준" 것이 아니라
  **같은 동작 키의 전형기 패스 중 36 cm보다 가까운 것이 L1에 없다.** 사용자 질문("이 정도로 없어?")에 대한 답은 이 패스에서는 "그렇다"이다.
- 같은 세션의 다른 패스들은 크게 바뀐다. 예: L1 #9 0.168 → **0.041 m**(기준 1000442_1 #1 → 1000564_1 #2), L1 #3 0.133 → **0.054 m**,
  L3 #34 0.507 → **0.011 m**(1000444_1 #63 → #69), L3 #39 0.445 → **0.003 m**, L3 #33 0.461 → **0.028 m**.
  L3 1000391_1은 후보가 16–122개로 많아 정렬의 효과가 크고, L1 1000389_1은 후보가 0–37개로 적어 효과가 작다.
- **3D 화면의 글자는 늘리지 않았다.** `hit_distance_m`은 JSON 응답에만 있고 `static/app.js`는 읽지 않는다(§7-8). `N개 중 k번째`·`[다른 기준 ▸]` 문구 그대로다.
  "다른 기준 ▸" 순환은 `referenceState.candidates`를 서버 순서대로 도므로 **가까운 순**으로 돈다 — 화면 코드는 한 줄도 고치지 않았다.
- **보고 전용 `nearest_raw`(§3.6).** 정렬 거리를 원 프레임 호장 중점(s ≈ 0.5)의 `hit`으로 바꾸면, 51패스 중 **16패스**에서 첫 후보가 달라진다.
  §1.1의 비대칭(정렬은 격자 중점 s ≈ 0.526, m3 키의 칸은 원 프레임 중점 s ≈ 0.5)이 실제로 짝을 바꾼다는 뜻이다.
  이번 판정에는 쓰지 않는다. 정리하려면 새 사전등록이 필요하다.

### R5. `build_spread_reference` 회귀 검사 (§8)

- 넣은 검사: `trainer/scripts/tests/test_build_spread_reference.py::test_builder_buckets_by_the_midpoint_cell_not_the_start_cell`.
  실데이터 세션 하나(김경호 20250831 L1 `1_1000389_1.csv`)만 심볼릭 링크로 담은 임시 루트에서 `build_from_root`를 돌리고,
  그 uv8 버킷 키 집합이 `service.pass_key_inputs` → `service.key_from`의 키 집합과 **같고**, 시작 프레임 UV로 만든 키 집합과는 **다르다**고 단언한다.
  두 칸이 갈린 패스가 3개 이상이라는 것도 같은 검사에서 단언한다(`assert split >= 3`) — 갈리지 않는 입력이면 뒤 단언이 공허하기 때문이다.
- **일부러 깨뜨림**: 빌더의 키 재료 호출을 `frames = service.pass_frames(raw); inputs = service.key_inputs(frames, raw_frames=frames)`로 바꿨다
  (`raw_frames`가 키워드 필수라 이름을 빼면 `TypeError`지만, 리샘플 격자를 원 프레임 자리에 넣으면 **조용히 첫 프레임 UV**가 된다 — 정확히 직전 검증자가 남긴 구멍이다).
  실패 메시지: `AssertionError: 빌더의 버킷 키가 비교 경로의 키와 다르다` / `Extra items in the left set: 'm3:vertical_down:none:1x1:center-far-high'`.
- 같은 되돌림 아래에서 **이웃 검사들은 그대로 통과했다**: 새 검사만 빼고 `test_build_spread_reference.py`·`test_midpoint_uv_key.py`·`test_spread_reference.py`를 돌리면 `21 passed`.
  직전 검증자의 지적("빌더의 키 UV 경로만 되돌려도 전체 스위트가 통과한다")이 사실이었고, 이 검사가 그 구멍을 막는다. F16은 발생하지 않았다.
- 이 검사는 P1과 독립이므로 P1을 되돌렸더라도 남긴다(§5).
