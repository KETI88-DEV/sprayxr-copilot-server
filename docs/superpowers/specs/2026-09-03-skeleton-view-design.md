# 스켈레톤 뷰 설계

작성 2026-09-03. 선행: `2026-09-02-world-axis-convention-design.md`(축 규약·메시 앵커),
`2026-08-31-multi-axis-correction-design.md`(교정 계약).

## 1. 무엇을 만드는가

원래 요청은 이것이었다.

> 두 자세를 나란히 비교하며 유사도가 나오고, 어긋난 부분을 정도에 따라 표현하고,
> 교정하는 텍스트를 출력하며, **교정을 적용했을 때의 예상 자세**가 나와서 얼마나
> 자세유사도가 높아지는지를 비교하는 프로그램.

숫자와 문장은 나오지만 **자세가 안 보인다.** 이 설계가 그것을 채운다.

한동안 막혀 있었고 세 가지가 풀렸다. **요가 실측이다**(`facing_yaw`가 HMD 회전에서
뽑고 IK를 안 탄다). **축 규약이 확정됐다**(유니티 Y-up). **벽면이 생겼다** — 레벨 메시가
풀어낸 정렬로 월드에 놓이고 착탄점이 그 면 위 **0.0000 mm**에 앉는다(UV R² 0.9999998).

## 2. 전신을 그린다. 강조는 가중치를 따른다.

전신 스켈레톤을 그린다. **시각적 강조가 채점 가중치를 그대로 따라간다.**

| 가중치 | 부위 | 화면 |
|---|---|---|
| 높음 | 머리(HMD) · 오른손(건) · 왼손(플래시) · 착탄점 | 고유색, 굵게, 편차 마커, 수치 라벨 |
| 낮음 | 어깨 · 팔꿈치 — 오른팔을 잇는 데 필요 | 같은 색조를 낮은 채도로, 라벨 없음 |
| 0 | 나머지 전신 | 조용한 중립 형태 — 선만, 마커·수치 없음 |

가중치 0인 부위도 **또렷하게 보인다.** 자세의 형태와 방향을 읽으려면 몸통과 다리가
있어야 하고, 그것이 전신을 그리는 이유다. 다만 시선을 끄는 장치 — 색, 굵기, 편차 마커,
숫자 — 는 **가중치가 있는 곳에만** 붙는다. 그래서 코치의 눈이 자동으로 채점이 보는
곳으로 간다.

### 화면 문구 규칙

**화면에 "사용하지 않음" 계열의 표현을 쓰지 않는다.** 강조가 약한 이유는 화면에서
**"핵심 지표에 가중치를 둔다"**로 설명되고, 그것이 실제로 일어나는 일이다 — 강조된
네 지점이 σ·교정·개선율을 전부 이끈다.

동시에 **재지 않은 것을 잰 것처럼 주장하지 않는다.** 가중치 0인 부위에는 수치도
편차 마커도 툴팁의 측정값도 붙지 않는다. 덜 강조하는 것과 없는 측정을 있다고 말하는
것은 다르고, 후자는 하지 않는다. 이 두 규칙은 충돌하지 않는다: 화면은 조용히 있을 뿐
거짓을 말하지 않는다.

**뼈 길이는 그 사람의 것이 아니다.** 리그 바인드 오프셋(상완 0.243 m, 전완 0.243 m)이
**여섯 작업자에서 전부 동일**하다 — 개인 체형이 아니라 범용 아바타다. 내부 문서와
개발자용 표시에는 남기고, 운영 화면에서는 조용한 각주로 둔다.

### D0. 전신의 출처는 CSV 회전 FK다

**BVH 파일은 저장소에 0개다**(`find -iname '*.bvh'` → 0). 남는 경로는 하나다.

**CSV 회전에서 FK.** 관절 `Rotation` 컬럼이 프레임마다 있고 `Position`은 바인드
오프셋이다. `trainer/scripts/pose_fk_csv.py`·`bvh_skeleton.py`가 이미 있다. 이 경로면
화면의 전신이 캡처와 같은 출처를 갖는다.

**골반이 월드가 아니다**(전체 아핀으로도 수평 두 축의 R²이 0.003~0.12, 선행 스펙 §3).
그래서 전신은 골반이 아니라 **실측 점에 맞춰 놓는다** — FK한 사슬을 머리·양손이 실측
위치에 가장 가깝도록 강체 정렬한다.

**잔차는 재고 기록하되 운영 화면에 상시 노출하지 않는다.** 계획의 첫 태스크가 그 값을
측정한다. 잔차가 크면 그 사실이 설계 판단을 바꾼다 — 전신을 더 조용하게 그리거나,
정렬을 개선하거나, 몸통까지만 그린다. 개발자 모드에서는 값을 그대로 보여준다.

## 3. 세 자세를 겹쳐 그리고, 층마다 켜고 끈다

| 층 | 무엇 | 기본 |
|---|---|---|
| `query` | 훈련생 패스 | 켬 |
| `reference` | 키가 일치하는 전문가 패스 | 켬 |
| `corrected` | 교정을 따랐을 때의 예상 | **끔** |

겹쳐야 편차가 보이고 끌 수 있어야 엉키지 않는다. `corrected`가 기본 꺼짐인 이유는 그것이
관측이 아니라 **예상**이기 때문이고, 켤 때 화면이 그렇게 말한다.

## 4. 좌표의 출처 — 여기가 틀리기 쉽다

### D1. 뷰는 월드를 나른다. `compare`의 트랙은 로컬이다.

`query_track` / `reference_track` / `fixed`는 전부 **스트로크 로컬**이다(`_local_tracks`).
그대로 그리면 벽이 있는 월드와 안 맞는다. 뷰는 `pass_frames`가 낸 `MeasuredFrame`의
**월드 좌표**에서 짓는다.

### D2. 교정 후 위치는 `AxisCorrection.unit`으로 더한다

`issued_shifts`는 스트로크 프레임 성분을 낸다. `issued_axes`가 내는 `AxisCorrection`은
**월드 단위벡터**(`unit`)와 크기를 함께 들고 있으므로, 한 점의 월드 이동은 발부된 축들의
`magnitude_cm/100 × unit` 합이다.

**이 경로를 써야 한다** — 문장·숫자 패널·시뮬레이션이 이미 같은 `issued_axes`에서 나온다.
별도로 계산하면 화면이 개선율과 **다른 이동**을 그린다.

### D3. 격자점을 그린다, 원본 프레임이 아니라

로컬 트랙은 격자점 **20개**로 리샘플된 것이고 원본은 패스당 수백이다. **채점이 보는 것은
격자점**이고 두 패스의 대응도 거기서 난다. 원본이 더 매끄럽지만 그리면 **그림과 숫자가
서로 다른 것을 기술**한다. 원본 궤적은 배경에 아주 흐리게만 허용하고, 비교·강조는
격자점에서만 한다.

## 5. 벽면은 있을 때만 그린다

메시 정렬은 **학습모드 레벨에만** 선다. 실전모드(`1-A` 등)는 다른 장면이라 그 착탄점을
학습모드 메시에 대면 3.4 m 뜬다(`_collect_level_hits` 독스트링). 현재 검증된 것은
**레벨 1뿐**이다(레벨 10은 UV R² 0.23~0.32).

정렬이 있으면 벽면을 그리고, 없으면 **그리지 않는다.** 있는 척 그리면 화면이 검증되지
않은 기하를 주장한다. 응답에서 `mesh`가 `null`인 것("정보 없음")과 `available: false`
("이 레벨에 검증된 정렬이 없음")를 구분한다 — 소비자가 두 상태를 다르게 다뤄야 하기
때문이고, 화면 문구는 둘 다 조용하다.

## 6. 응답 변경

```
view : {
  grid_n: int,
  layers: {
    query:     {head:[Vec3], right:[Vec3], left:[Vec3|null], hit:[Vec3|null],
                joints: {<name>: [Vec3]}},
    reference: {...같은 모양...},
    corrected: {...같은 모양...} | null
  },
  mesh:    {level:int, available:bool, vertices:[Vec3], triangles:[[int,int,int]]} | null,
  weights: {<name>: float},          // 0.0 ~ 1.0, 채점 가중치
  fit:     {residual_m: float, source: "fk_csv"} | null   // 개발자 표시용
}
```

`weights`가 이 스키마의 중심이다. **화면의 강조는 전적으로 이 숫자에서 파생된다** —
색의 채도, 선 굵기, 편차 마커와 수치 라벨의 유무가 전부 `weights[name]`의 함수다.
등급 이름("미사용" 같은)이 스키마에 없으므로 **화면으로 새어 나갈 라벨 자체가 없다.**
새 관절을 `weights`에 안 넣으면 강조 규칙이 그 관절을 다룰 수 없다 — 테스트가 막는다.

`fit.residual_m`은 전신 정렬 잔차다. **개발자 모드에서만** 표시한다.

## 7. 화면

- 3D 뷰(three.js). 드래그 회전, 휠 확대, 벽 정면·측면 프리셋.
- **강조는 `weights`에서 나온다** — 색·굵기·마커·라벨이 전부 그 함수. 하드코딩한
  부위 목록으로 분기하지 않는다.
- 층 토글 셋(`query`/`reference`/`corrected`), 벽면 토글.
- 발부한 축을 화살표로 — 색은 σ.
- 값이 없으면 `—`이고 `0`이 아니다. JS에서 `0`도 falsy이므로 `||`가 아니라 `??` 또는
  `typeof x === "number"`.
- 문구는 있는 것을 말한다. 없는 것을 열거하지 않는다.

## 8. 위치

`trainer/pose_lab/static`. 데이터가 거기 있고 빌드 단계가 없다. 관절 추정이 서버에 있으니
나중에 `demo-ui`(React)로 옮길 때 **렌더러만** 다시 쓴다.

three.js는 CDN에서 받는다 — 오프라인이면 3D가 안 뜨고, 그때도 숫자 패널은 그대로
동작해야 한다.

## 9. 테스트

- 어깨 추정이 요를 **실제로** 쓴다 — 요를 바꾸면 어깨가 따라 움직인다.
- 2-본 IK: 손이 팔 길이보다 멀면 팔을 편 상태로 떨어뜨리고 **그 사실을 낸다.**
  조용히 뼈를 늘리지 않는다.
- 팔꿈치 각도를 손으로 유도해 고정한다.
- `corrected` 층이 `issued_axes`가 낸 이동과 **정확히** 같다. 별도 계산 경로가 없다.
- 격자점 수가 `_local_tracks`의 리샘플 수와 같다 — 그림과 채점이 같은 표본을 본다.
- 검증된 정렬이 없는 레벨에서 `mesh.available`이 `false`이고 벽면이 안 그려진다.
- **`weights`가 모든 관절을 덮는다** — 빠진 관절이 있으면 실패한다.
- **가중치 0인 관절에 수치·편차 마커가 붙지 않는다** — 렌더러가 `weights`를 실제로
  읽는지 확인한다. 가중치를 바꾸면 강조가 따라 바뀐다.
- `fit.residual_m`이 실제 잔차다 — 정렬을 흔들면 값이 따라 움직인다.

성질을 보호한다고 이름 붙인 테스트는 **그 성질을 일부러 깨뜨려 실패를 확인한 뒤에만**
인정한다. 이 저장소에서 실패할 수 없는 단언이 열 건 넘게 나왔고, 매번 리뷰어가 직접
무력화해서 찾았다.

## 10. 범위 밖

| 항목 | 이유 |
|---|---|
| `pass_segmentation`의 Z-up 경로 | 별건이고 **이것보다 우선일 수 있다** — 출하된 `mcp_servers/pose_estimation.py`가 그 산출물을 쓴다 |
| 레벨 2~10 메시 정렬 | 별건. 레벨 10은 아직 신뢰 불가 |
| 각도 기반 교정 | 법선이 생겼으나 레벨 1뿐 |
| 허리 교정 | 데이터에 없음. 확보되면 각도로 |
| React 이전 | 관절 추정이 서버에 있으니 나중에 렌더러만 |

## 11. 열린 위험

- **가중치 강조가 얼마나 강해야 하는지 모른다.** 너무 약하면 전신이 시선을 흩고,
  너무 강하면 나머지 몸이 사실상 안 보인다. 실제 화면에서 조정이 필요하다.
- **추정 팔이 틀릴 수 있다.** 어깨 오프셋은 가정이고 팔꿈치는 IK다.
- 벽면이 레벨 1에만 선다. 다른 레벨에서 안 그려지는 것이 **정상 동작**이지만
  고장으로 읽힐 수 있다.
- 전신 정렬 잔차가 클 수 있고, 그러면 가중치 0인 부위가 실제 자세와 어긋난 채로
  그려진다. D0의 측정이 그 크기를 먼저 알려주고, 크면 설계를 조정한다.
