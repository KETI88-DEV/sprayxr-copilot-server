# KETI AI Co-Pilot API v1.5 연동 설계 — 우리 저장소를 AI 백엔드로

**Date**: 2026-08-03
**Status**: Draft (design) — 섹션 1·2 승인, 섹션 3~7 승인 대기
**Scope**: KETI가 별도로 운영하는 `/api/v1/*` 서비스(`keti-xr-lab.iptime.org:58000`, FastAPI + MySQL + SQLAdmin)가 우리 AI 파이프라인을 호출할 수 있도록, 우리 쪽에 안정적인 HTTP seam `/api/ext/v1/*`을 만든다. `/api/v1/*` 자체는 구현하지 않는다. 기존 `/api/sim/*`은 그대로 유지한다.

**근거 문서**: `docs/AI_CoPilot_API_정의서_v1.5.pdf` (v1.5, 2026-07-31, 한국전자기술연구원 정성오 연구원)

---

## 1. 목표 / 비목표

### 목표

- KETI 서비스가 **base URL 하나만 설정하면** 우리 AI에 연결되도록 한다. 상대 팀이 매핑 코드를 새로 쓰지 않아도 되게 한다.
- v1.5의 세 가지 AI 요구를 각각의 지연 등급에 맞는 엔진으로 처리한다: 실시간 이상 경고(룰), 질의응답(LLM), 최종 종합 평가(LLM).
- `session_id`를 받지 않는 `/api/v1/copilot/query`에도 세션 컨텍스트를 부여한다.
- KETI 어휘(`R-UP-01`, `SCENARIO_REAL_1A`, `W-017`, `over-app`)가 파이프라인 내부로 새지 않게 한다.
- 상대 서버에 접속하지 못하는 상태에서도 연동 신뢰도를 확보한다.

### 비목표

- `/api/v1/*` 엔드포인트 구현. 세션 DB, MySQL, SQLAdmin, 이상탐지 SSE 채널은 전부 KETI 소유다.
- `/api/sim/*` 폐기. 두 표면은 하나의 세션 store 위에 놓인 두 개의 어댑터로 공존한다.
- Unity 클라이언트 코드.
- 인증·인가. v1.5에는 어떤 엔드포인트에도 인증이 없다(§10 OQ-6).
- `AgentPipeline.run()` 동작 변경. 평가 재현성 경로는 그대로 둔다.
- Qwen3-VL 비전 분석. 이번 범위에서 제외하고 별도 트랙으로 넘긴다(§9.3).

## 2. 배경 — 확인된 사실

세 가지를 직접 확인했고, 설계는 전부 여기서 나온다.

**2.1 상대 서버에 접속할 수 없다.**
DNS는 `keti-xr-lab.iptime.org → 220.120.108.50`으로 해석되지만 TCP `:58000` 연결이 타임아웃한다(45초 × 3회, `/openapi.json`·`/docs` 모두). 따라서 라이브 OpenAPI와 PDF v1.5를 대조하지 못했고, **이 설계의 유일한 출처는 PDF다.** 동시에 이것은 설계 제약이기도 하다 — 역방향 연결(우리 → 그들)을 전제하는 구조는 근거가 없다.

**2.2 저장소에 이 계약의 흔적이 전혀 없다.**
`keti`, `58000`, `api/v1`, `copilot/query`, `SCENARIO_REAL`, `mysql`을 전체 `.py/.ts/.tsx/.md/.json/.yaml`에서 검색해 코드 참조 0건이다. 신규 표면이며, 기존 코드를 고쳐 맞추는 작업이 아니다.

**2.3 두 계약은 거의 모든 축에서 다르다.**

| 축 | 우리 `:8120` | KETI v1.5 `:58000` |
|---|---|---|
| 식별자 | `level_id: TR-L01`, `worker.trainee_id` | `scenario_id: SCENARIO_REAL_1A`, `user_id: W-017` |
| 숙련도 | `beginner \| intermediate \| advanced` | `expert \| novice` |
| 구역 | `A-1 / A-2 / A-3` | `R-UP-01 / R-LO-01` |
| 런타임 | 호출당 이벤트 1건, 동기 응답에 `kind:"anomaly"` | Trigger ON→OFF당 90 FPS 배치, 이상은 **별도 SSE 채널**로 push |
| 질의 | `POST /api/chat`, SSE, 세션 스코프 `environment` | `POST /api/v1/copilot/query`, **session_id 없음, 스트리밍 없음** |
| 라우팅 | 서버 3-way (`training_realtime\|training_review\|fast`) | 클라이언트 선언 5-way (`task_type`) |
| 최종 평가 | JSON `SessionSummary` | multipart: 2048×2048 heightmap PNG + 전체 CSV → Qwen3-VL 리포트 |
| 봉투 / 상태 | bare JSON, 단일 슬롯 in-memory | `{status, code, message, data}`, MySQL |

## 3. 아키텍처

```
Unity VR 클라이언트
     │  /api/v1/*   (KETI 계약)
     ▼
KETI :58000    FastAPI + MySQL + SQLAdmin + 이상탐지 SSE       ← KETI 소유
     │  HTTP. 그들이 호출하고 우리가 응답한다. base URL 하나.
     ▼
우리 AI 백엔드 :8120    /api/ext/v1/*                          ← 이번 작업
     ├─ Tier 0  open / verdict / close  → MCP :8100 룰 전용   p99 < 500 ms
     ├─ Tier 1  copilot query           → AgentPipeline + RAG  §8.2 예산
     └─ Tier 2  session report          → AgentPipeline        분 단위, job+poll
              │
              └── SimSessionStore (확장: session_id 키, user_id 인덱스)
```

### 3.1 세 가지 불변 규칙

**우리는 절대 호출자가 되지 않는다.** 콜백·웹훅·역방향 push가 없다. §2.1에서 확인했듯 우리는 상대 서버에 접속할 수 없고, 앞으로 가능해진다는 근거도 없다. 모든 교환은 그들의 요청과 우리의 응답이다.

**Tier 0은 LLM에 도달할 수 없다.** 성능 목표가 아니라 구조 규칙이다. 라우터가 MCP를 직접 호출하며 `AgentPipeline`을 참조하지 않는다. 1회 분사는 수 초이고 RAG-only 응답은 p50 31.4초·p90 59.1초(`findings.md`)다. LLM 판정은 훈련생이 이미 떠난 구역을 경고하게 된다. 반면 `anomaly_detection`·`dft_judge`는 실제 로직이며 1 ms 미만이다.

**Tier 2는 단일 장기 요청이 아니라 job + poll이다.** `POST /session/report` → `{job_id}`, `GET /session/report/{job_id}` → `pending|done|failed`. KETI의 `/sessions/complete` 핸들러는 Unity와의 동기 계약을 유지하려면 이 poll에서 블록하면 된다. 이유는 두 가지다 — 분 단위 GPU 작업이 TCP 순단 하나로 폐기되면 안 되고, 결과가 그들의 MySQL에 기록될 때까지 살아 있어야 한다. 엔드포인트 하나를 추가하는 대가로 시스템에서 가장 비싼 호출에 크래시 내성을 얻는다.

## 4. 세션 정체성

### 4.1 문제

`/api/v1/copilot/query`는 `{user_id, prompt, task_type, use_rag}`만 보내고 `session_id`가 없다. 우리 답변 품질의 근거인 현재 구역·최근 텔레메트리·이상 횟수가 전부 세션 상태에서 오므로, 그대로 두면 모든 질의가 맥락 없이 답변된다.

### 4.2 해법 — 계약 변경 없이 해결된다

`/api/v1/telemetry/sequence`는 `user_id`와 `session_id`를 **함께** 보낸다. 이 값으로 인덱스를 만든다.

- `SimSessionStore`를 단일 슬롯에서 `session_id → SimSessionState` 맵으로 확장하고, `user_id → 최근 활성 session_id` 인덱스를 함께 둔다.
- 기록: `session/open`(생성), `sequence/verdict`(구역·이상 갱신), `session/close`(종료).
- 조회: `copilot/query`가 `user_id`로 최근 활성 세션을 찾아 `environment`를 구성한다.
- 해당 사용자의 활성 세션이 없으면 **세션 없는 모드로 강등**한다. 지식 질문은 정상 답변되고 상황 근거만 빠진다.

### 4.3 기존 동작 보존

`SimSessionStore`의 공개 메서드 시그니처(`start` / `runtime` / `end` / `current`)는 유지한다. 내부만 맵으로 바뀌고 다음이 추가된다.

```python
def get(self, session_id: str) -> SimSessionState | None: ...
def latest_for_user(self, user_id: str) -> SimSessionState | None: ...
# start()에 선택 인자 user_id: str | None = None 추가 (기본 None, 기존 호출부 무변경)
```

`current()`는 **가장 최근에 갱신된 세션**을 반환한다. 단일 세션 사용에서는 관측 동작이 지금과 완전히 같으므로 `/api/sequence/{level_id}`, `/api/sim/session`, live `environment`, 그리고 codegraph가 보고한 27개 호출부와 기존 테스트가 그대로 통과한다. `runtime()`·`end()`의 "모르는 session_id면 `None`" 계약도 유지된다.

### 4.4 우리는 정본이 아니다

정본은 그들의 MySQL이다. 우리 store는 **경계 있는 in-memory 캐시**이며 개수와 수명으로 축출한다(기본 64세션 / 6시간, 설정값). 재시작하면 세션은 다음 텔레메트리 호출로 다시 성립하고, 영속 손실은 없다. 이 문장이 "왜 우리 쪽에 DB를 두지 않는가"에 대한 답이다.

## 5. 엔드포인트 seam

접두사 `/api/ext/v1`. 각 엔드포인트는 KETI 필드명을 **그대로** 쓰는 wire shape을 가지며, 그래야 상대 핸들러가 통과(passthrough)로 끝난다.

| 우리 | 그들의 호출부 | Tier | 반환 |
|---|---|---|---|
| `POST /session/open` | `/sessions/start` | 0 | `recommended_flow`, `guidance` |
| `POST /sequence/verdict` | `/telemetry/sequence` | 0 | SSE로 밀어 넣을 이상 페이로드 |
| `POST /copilot/query` | `/copilot/query` | 1 | `answer`, 인용 |
| `POST /session/report` | `/sessions/complete` | 2 | `job_id` |
| `GET /session/report/{job_id}` | `/sessions/complete` poll | 2 | 리포트 또는 `pending`/`failed` |
| `POST /session/close` | `/sessions/end` | 0 | ack |

### 5.1 `sequence/verdict` — 이 설계의 핵심 세부

응답은 §7의 공통 봉투를 쓰고, **`data` 필드가 그들의 `anomaly_detection` SSE 이벤트 `data:` 페이로드와 정확히 일치**한다.

```json
{"status":"SUCCESS","code":200,"message":"...",
 "data":{"session_id":"1_1000053_1","zone_id":"R-LO-01","sequence_id":"SEQ005",
         "thickness":185,"status":"over-app","message":"하단 좌측 영역 도막 두께 과다 도포 발생! ..."}}
```

그들의 핸들러는 `data`를 꺼내 그대로 SSE 채널에 전달한다. 필드 매핑이 없으므로 드리프트할 것도 없다. 이상이 아니면 `data`는 `{"is_anomaly": false}`이고 그들은 아무것도 push하지 않는다.

입력은 v1.5 §3.3 `/telemetry/sequence` 본문 전체를 그대로 받는다. 90 FPS `sequence_info` 배열은 Tier 0 판정에 쓰지 않는다 — 요약 통계 `sequence_result`로 충분하다. 세션 store에는 배열 전체가 아니라 **마지막 프레임의 `tool_pos_rot`, 프레임 수, `sequence_result` 요약**만 보관한다. 원본 시계열의 정본은 그들의 MySQL이다(§4.4).

### 5.2 `task_type` 매핑

그들의 클라이언트 선언 5-way를 우리 3-way 라우터에 `force_route`로 넘긴다. `run_streaming()`이 이미 `force_route`를 지원하므로(AGENTS.md: "classifies on instruction only via `force_route`") 새 기계장치가 아니라 배선이다.

| KETI `task_type` | 우리 라우트 |
|---|---|
| `trajectory_recomm` | `training_realtime` |
| `error_analysis` | `training_realtime` |
| `pose_recomm` | `training_review` |
| `knowledge_search` | `fast` |
| `qna` | `fast` |

`use_rag: 'N'`이면 검색을 건너뛴다. 충돌 사례가 하나 있다 — `error_analysis` + `use_rag: 'N'`은 근거 없이 진단을 요구한다. **규칙: 검색 여부는 `use_rag`가, 라우팅은 `task_type`이 결정한다.** 이때 답변 계약에서 `[근거]`를 뺀다. 실제로 근거가 없기 때문이다(OQ-4).

### 5.3 파일 배치

기존 `trainer/demo_api/` 평면 구조와 250 LOC 상한을 따른다.

| 파일 | 책임 |
|---|---|
| `keti_contracts.py` | ext 경계 Pydantic 모델. KETI wire shape 미러, `extra="forbid"` |
| `keti_vocab.py` | 어휘 변환 테이블. 순수 함수, I/O 없음 |
| `keti_router.py` | 6개 엔드포인트와 `{status, code, message, data}` 봉투 |
| `keti_report_jobs.py` | Tier 2 job store (제출·상태·결과·축출) |
| `trainer/scripts/keti_reference_proxy.py` | `/api/v1/*` 참조 구현 (§8.2) |

## 6. 어휘 경계

`keti_vocab.py` 한 곳에 테이블로 모은다. 순수 함수이며 I/O가 없다.

| 종류 | 변환 | 상태 |
|---|---|---|
| 구역 | `R-UP-01` ↔ `A-1` … | **테이블 미확정 (OQ-1)** |
| 시나리오 | `SCENARIO_REAL_1A` ↔ `TR-L01` | **테이블 미확정 (OQ-2)** |
| 숙련도 | `novice→beginner`, `expert→advanced` | 확정. 손실 있음 — 우리 `intermediate`는 그들 입력에서 생성될 수 없다 |
| 도포 상태 | `normal\|over-app\|under-app` ↔ 우리 이상 종류 | 확정 |
| 속도 단위 | `avg_speed_mms`(mm/s) ↔ `speed_m_per_s`(m/s), ×1000 | 확정 |
| 거리·두께 | `avg_distance_mm`(mm), `avg_thickness_um`(µm) | 단위 동일, 변환 없음 |

**강제 규칙**: KETI 식별자는 `keti_vocab.py`와 `keti_router.py` **밖에 나타나지 않는다.** 파이프라인·MCP·세션 store·UI 어디에서도 `R-UP-01`이나 `W-017`을 보지 않는다. 이로써 AGENTS.md의 명명 규약(`TR-L01`, `A-1/A-2/A-3`)이 내부에서 계속 참이고, 구역 테이블이 바뀌어도 한 파일 수정으로 끝난다.

**테이블 확정 전 잠정 동작**: 미지의 구역·시나리오 코드는 예외를 던지지 않고 `unresolved_zone_id` 경로로 흘린다(`sim_session.py`의 기존 규칙과 동일 — 위치를 옮기지 않고 관측만 한다). Tier 0·Tier 1은 이 상태에서도 동작하며, 정확한 구역 귀속만 보류된다.

## 7. 오류 처리와 동기 타임아웃

- **봉투**: `{status, code, message, data}`는 `/api/ext/v1/*` 경계에서만 씌운다. 내부 코드는 bare JSON을 유지하며, 인코더 함수 하나가 담당한다.
- **Tier 0은 fail-open**이다. MCP가 죽어도 `{"is_anomaly": false, "degraded": true, "reason": "..."}`를 HTTP 200으로 반환하고 절대 500을 내지 않는다. 경고 경로 고장이 훈련생의 세션을 깨서는 안 된다. 그들의 SSE는 이벤트를 받지 않을 뿐이다.
- **Tier 1은 상한이 필요하고, 그 값은 Task 8이 정한다.** RAG-only p90이 59.1초인데 동기 HTTP 호출이 그 지연을 내면 대부분의 클라이언트 기본 타임아웃을 넘긴다. 설정값 `query_timeout_ms`를 두고 **만료 시 504가 아니라 가용한 최선의 답(RAG 근거, 도구 생략, `degraded: true`)을 반환**한다. 부분적으로 답하는 코칭 시스템이 타임아웃하는 쪽보다 낫다. 잠정 기본값 60000, Task 8 측정 후 `p95(total) + margin`으로 교체한다(OQ-5).
- **Tier 2 실패는 HTTP 오류가 아니라 상태다.** `{"state": "failed", "reason": "..."}`를 200으로 반환해 그들의 poll 루프를 단순하게 유지한다. 완료 job은 24시간 또는 100건까지 보관한다.
- 그들의 `/telemetry/sequence/test-anomaly`(개발용 이상 주입)에 대응하는 우리 엔드포인트는 없고 필요하지도 않다. 그들 쪽 fixture 주입기다.

## 8. 테스트 전략

상대 서버에 접속할 수 없으므로(§2.1) 연동 신뢰도는 서버가 아니라 산출물에서 나와야 한다.

### 8.1 골든 픽스처

v1.5의 모든 페이로드 예시(§3.1 세션 시작, §3.3 시퀀스, §3.4 질의, §3.5 SSE 이벤트, §3.6 complete)를 JSON 픽스처로 커밋한다. 각 픽스처가 `extra="forbid"` 모델에 대한 테스트가 된다. 문서의 예시가 우리 모델을 통과하지 못하면 그것이 곧 계약 불일치 신호다.

### 8.2 참조 프록시

`/api/v1/*`를 그들의 핸들러가 **마땅히 그래야 할 모습**대로 구현한 작은 로컬 FastAPI 앱 — 우리 ext API로의 얇은 통과. 두 가지 역할을 겸한다.

1. 우리 쪽 end-to-end 테스트 하니스.
2. KETI에 넘기는 산출물. 그들의 실제 핸들러가 어긋나면, PDF를 놓고 논쟁하는 대신 **돌아가는 것과의 diff**로 드러난다.

AGENTS.md의 SSE 주의사항이 여기에 적용된다 — 종료되지 않는 SSE 라우트를 Starlette `TestClient`로 구동하지 않는다. 이상탐지 스트림은 프록시 쪽에 있으므로 순수 async generator를 anyio로 검증하거나 실제 uvicorn을 띄운다.

### 8.3 단위·계약 테스트

| 대상 | 방식 |
|---|---|
| `keti_vocab` 변환 | 순수 단위. 왕복 변환, 미지 코드 → 예외 없이 unresolved, 단위 ×1000 |
| `SimSessionStore` 확장 | 다중 세션 격리, `user_id` 인덱스, 축출, `current()` 하위호환 |
| Tier 0 판정 | fake MCP 주입. 정상·이상·MCP 장애(fail-open) |
| Tier 1 라우팅 | `task_type` 5종 → `force_route` 매핑, `use_rag='N'` 충돌 규칙 |
| Tier 1 타임아웃 | fake 파이프라인으로 만료 시 degraded 응답 검증 |
| Tier 2 job | 제출→pending→done/failed 전이, 축출 |
| 봉투 | ext 경계에서만 래핑되고 내부는 bare임을 고정 |

### 8.4 기존 게이트

`docker exec -w /workspace ship-paint-trainer python3 -m pytest trainer mcp_servers -q`가 계속 통과해야 한다. 특히 §4.3의 하위호환 주장(기존 27개 호출부와 테스트 무변경)은 이 스위트가 증명한다. UI 표면 변경이 없으므로 `npm run build:web`은 이번 범위에서 게이트가 아니다.

### 9.2 Task 8 재해석

기존 게이트는 첫 `message_delta`까지의 TTFT였다. KETI의 `/copilot/query`는 동기 JSON이므로 **그 경계에 TTFT가 존재하지 않는다.** Task 8은 이제 라우트별 **총 시간 백분위**를 보고해야 하며, 그 값이 §7의 `query_timeout_ms`를 정한다. TTFT 게이트는 여전히 SSE인 우리 데모 UI에 대해서는 유효하다.

이것이 항목 2~4가 연기되는데도 Task 8이 남는 이유다. Task 8은 연동의 입력값이다.

### 9.3 Qwen3-VL을 v1에서 뺀다

v1.5 §3.6은 2048×2048 heightmap에 대한 Qwen3-VL 분석을 명시한다. 우리는 텍스트 전용 Qwen3.6-27B를 쓰고 `vlm_analysis`는 stub이다. 새 모델·새 VRAM 예산·새 평가가 필요하고, 항목 2~4가 막 비운 바로 그 A40을 두고 경쟁한다.

**Tier 2를 텍스트 전용으로 먼저 출시한다.** `final_score`, `rank`, `summary_stats`, `defects_detected`, `ai_coaching_report`, `rag_guidance`는 전부 `result` 통계 + 텔레메트리 CSV + RAG에서 도출된다. 그들의 응답 계약의 **모든 필드가 실제 값으로 채워지며 stub이 아니다.** heightmap이 더하는 것은 *공간적* 결함 국소화이고, 이는 진짜 가치가 있지만 분리 가능하며, 계약을 건드리지 않고 두 번째 트랙으로 들어온다.

결과적으로 새 모델 작업을 시작하기 전에 세 Tier 전부가 연결된 end-to-end 시스템을 얻는다.

### 9.4 구현 순서

1. `keti_vocab` + `keti_contracts` + 골든 픽스처 (외부 의존 없음, 전부 순수)
2. `SimSessionStore` 다중 세션 확장 (하위호환 증명이 핵심)
3. Tier 0: `session/open`, `sequence/verdict`, `session/close`
4. 참조 프록시 + end-to-end 테스트 → **이 시점에 KETI에 전달 가능**
5. Tier 1: `copilot/query` (Task 8 결과로 타임아웃 확정)
6. Tier 2: `session/report` job + 텍스트 전용 리포트

4단계가 첫 번째 전달 지점이다. Tier 0만으로도 그들의 실시간 이상 경고가 실제 동작한다.

## 10. 열린 질문 (KETI 확인 필요)

각 항목에 **확정 전 잠정 동작**을 함께 정의한다. 답을 기다리는 동안에도 구현이 막히지 않게 하기 위해서다.

| ID | 질문 | 잠정 동작 |
|---|---|---|
| OQ-1 | 전체 구역 코드 목록과 대응 리그. PDF에는 `R-UP-01`, `R-LO-01`만 나온다. 우리는 SP0035 기준 `A-1/A-2/A-3`이다. | 미지 코드는 `unresolved_zone_id`로 관측만 하고 위치를 옮기지 않는다. Tier 0·1은 정상 동작한다. |
| OQ-2 | 전체 `scenario_id` 목록과 `level_id` 대응. | 미지 시나리오는 `TR-L01` 기본 flow로 처리하고 로그에 남긴다. |
| OQ-3 | **`result`가 JSON 문자열 1개인가, 개별 form 필드 8개인가.** PDF p.14 표는 개별 필드를 나열하는데 같은 절이 `result` JSON 문자열을 문서화하고, p.18 Unity 예제는 개별 필드만 보내고 `result`를 보내지 않는다. 문서가 자기모순이다. | 둘 다 받는다. `result`가 있으면 우선하고, 없으면 개별 필드에서 조립한다. |
| OQ-4 | `task_type: error_analysis` + `use_rag: 'N'` 조합의 의도. 근거 없는 진단 요구다. | §5.2 규칙 적용 — 라우팅은 `task_type`, 검색은 `use_rag`, 답변에서 `[근거]` 생략. |
| OQ-5 | Unity가 `/copilot/query`에 거는 HTTP 타임아웃 값. | `query_timeout_ms = 60000` 잠정. Task 8 후 `p95(total) + margin`. |
| OQ-6 | 인증 계획. v1.5에는 인증이 없고, `/telemetry/sequence/test-anomaly`는 임의 세션에 가짜 이상을 주입할 수 있는 **비인증 공개 쓰기**다. | 우리 ext API는 신뢰 네트워크 전제로 배포하고, 인증이 도입되면 헤더 통과 방식으로 대응한다. |
| OQ-7 | **이상 판정의 주인이 누구인가.** `sequence_result.status`(`over-app`/`under-app`)가 Unity에서 이미 결정된 채로 온다. 우리가 다시 분류하면 클라이언트와 모순될 수 있다. | 그들의 `status`를 사실로 받아들이고, 우리는 **원인과 조치 문구**를 생성한다(분류가 아니라 설명). 모순 시 그들 값을 우선한다. |
| OQ-8 | `skeleton_joints` 타입. 표는 `Array[Object]`인데 모든 예시는 관절명을 키로 하는 객체다(`{"RightHand": {...}}`). 예시끼리는 일관되므로 표가 틀린 것으로 보인다. | 객체(맵)로 파싱한다. 배열이 오면 관절명 키로 정규화한다. |
| OQ-9 | `pressure` 단위. PDF는 `(bar/psi)`로 병기하는데 두 단위는 약 14.5배 차이다. 예시값 150.0은 psi로는 타당하고 bar로는 비현실적이다. | psi로 해석한다. 임계값 판정에 쓰지 않으므로 오해석의 영향은 기록 값에 국한된다. |
| OQ-10 | 오타 확인: p.14 `ssession_id`, `avg_speed_mms` 2회 중복(두 번째는 설명 없음). | `session_id`로 읽고 중복 필드는 1개로 취급한다. |

OQ-1·OQ-2는 §9.4의 1단계에 필요하지만 잠정 동작으로 우회 가능하므로 **구현 착수를 막지 않는다.** OQ-3은 Tier 2(6단계)에서만 필요하다.
