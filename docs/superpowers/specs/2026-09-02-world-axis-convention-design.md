# 월드 축 규약 설계

작성 2026-09-02. 근거: `.superpowers/spikes/2026-09-02-vertical-axis-blast-radius.md`,
`.superpowers/spikes/2026-09-02-level-mesh-matching.md` (둘 다 이 스펙과 함께 커밋).

## 1. 무엇이 틀렸는가

**캡처 CSV의 월드 좌표는 유니티의 것이다 — Y가 위, 왼손 좌표계.** 그런데 코드는 Z를 수직으로
다룬다.

`measured_pose`는 CSV의 X·Y·Z 컬럼을 **재배열 없이** 읽는다(`simulator_csv.vec3` →
`_position`). 그래서 유니티 좌표가 그대로 채점기에 도달하는데:

| 위치 | 현재 | 전제 |
|---|---|---|
| `measured_score.WORLD_UP` | `(0.0, 0.0, 1.0)` | Z가 위 |
| `measured_score._axis_components` | `up_cm = world[2]`, `plane = (world[0], world[1], 0)` | Z가 위 |
| `stroke_frame.stroke_basis` | `_orthogonalized(WORLD_UP, forward)` | Z가 위 |
| `motion_key.heading_word` / `body_placement` | `cos(yaw)·d[0] + sin(yaw)·d[1]` | X·Y가 수평 |
| `measured_pose.facing_yaw` | `atan2(forward[1], forward[0])` | X·Y가 수평 |

### 세 가지 독립 확인

1. **위치만으로**(회전 규약 무관): `(머리 − 왼손)`의 Y 성분이 네 작업자에서 +0.315 / +0.351 /
   +0.374 / +0.414 m이고 **99~100% 프레임에서 양수**다. X와 Z는 평균 ≈0에 양수비율 약 50%.
2. **HMD 회전에서**: 머리의 위 벡터 평균이 `(+0.030, +0.705, −0.061)`, Y 성분의 산포가 가장 좁다.
3. **FBX가 선언**: 레벨 메시 파일이 `UpAxis = Y`를 직접 적고 있다.

사용자가 유니티 좌표계임을 확인했다(2026-09-02).

## 2. 왜 640개 테스트가 전부 통과했는가

축 이름은 데이터 **안**에서 검증할 수 없다. "어느 쪽이 아래인가"는 세상에 관한 사실이고,
단위 테스트는 그것을 물을 수단이 없다. 스켈레톤을 그리려 한 것이 이 프로젝트에서 그 질문을
처음 강제했다.

한동안 "점수는 기저 불변이라 무사하다"고 판단했다. **그 판단은 틀렸다** — §3 참조.

## 3. 영향 범위 (실측, 사전등록 200쌍 표집 · 시드 20260828)

| 항목 | 결과 |
|---|---|
| 점수 / 결합 σ | **불변이 아니다.** 최대 \|Δ점수\| 0.799, 중앙 0.091 (n=157) |
| 교정 축 선택 | 양쪽 발동 43쌍 중 **같은 축은 55.8%**(24/43) |
| 교정 문장 | 88쌍 중 **85쌍(96.6%)** 문구가 바뀜. **범주** 변경 44.2%(19/43) |
| 구체적 피해 | 위아래 ↔ 벽거리 뒤바뀜 **6쌍** (수직→벽 1, 벽→수직 5) |
| 축별 크기 | 비슷(벽 ~24cm, 수직 ~35–42cm, 진행 ~31cm) — **크기가 아니라 어느 축이 메시지를 나르는가가 뒤섞인다** |
| **동작 키 버킷** | **200개 중 193개(96.5%)가 다른 버킷으로 이동** |
| 머리 자세 | 양쪽 발동 14쌍 중 **8쌍(57%)이 높이 ↔ 벽거리로 뒤집힘** |

### 점수가 불변이 아닌 이유 (중요)

정규직교 논거는 **고정된 벡터 하나**를 두 번 분해할 때만 성립한다. 실제 경로는 그렇지 않다.

`service._local_tracks`가 패스의 리샘플 격자점 **20개마다** 그 점의 접선으로 **각자의**
`stroke_basis`를 만들고, 질의·레퍼런스를 그 점의 로컬 좌표로 옮긴다. `score_track`은 그 20개
로컬 차이를 **평균 내고**, 그 평균을 **하나의 대표 기저**로 `_axis_components`에 넘긴다.

서로 다른 기저에서 적힌 벡터를 평균 내고 또 다른 단일 기저로 재투영하는 것은 고정 벡터의 기저
변환이 아니다. `WORLD_UP`을 바꾸면 20개 기저가 **각자 다르게** 회전하므로 평균되는 좌표 자체가
바뀐다.

측정 하네스가 현재 파이프라인을 157쌍 전부 **비트 단위로** 재현하고, 재구현이 `up_index=2`에서
원본과 무작위 2만 회 일치함을 먼저 확인한 뒤 이 결론에 도달했다.

**이 설계의 범위 밖이다.** §7 참조.

## 4. 설계

### D1. 규약이 사는 곳 하나 — 상수가 아니라 연산

신규 `trainer/scripts/world_axes.py`. 결함이 생긴 이유는 규약이 **네 곳에 리터럴로** 흩어져
있었기 때문이다. 상수만 모으면 호출자가 다시 `world[2]`를 적을 수 있다. 그래서 **연산을** 모은다.

```python
UP_INDEX: Final = 1                      # 유니티 Y-up
UP: Final[Vec3] = (0.0, 1.0, 0.0)
HORIZONTAL_INDICES: Final = (0, 2)       # X, Z
HANDEDNESS: Final = "left"               # 유니티. 외적의 방향 감각이 오른손계와 반대다.

def vertical_of(v: Vec3) -> float        # 수직 성분
def horizontal_of(v: Vec3) -> tuple[float, float]
def flatten(v: Vec3) -> Vec3             # 수직 성분을 0으로
def yaw_of(forward: Vec3) -> float | None  # 수평면 방위. 수평 성분이 없으면 None
```

`yaw_of`는 `heading_word` / `body_placement`가 쓰는 전방 성분 정의(`cos(yaw)·h0 + sin(yaw)·h1`)와
같은 수평 축 쌍을 써야 한다. 그 대응이 깨지면 몸 기준 축이 조용히 월드 방위각으로 돌아간다.

**왼손 좌표계를 여기 적는다.** `stroke_basis`가 `_cross(forward, up)`으로 법선을 만드는데
외적의 방향 감각은 손잡이에 따라 뒤집힌다. 현재 코드는 건 위치로 법선 부호를 다시 고르므로
자체 교정되지만, 새 외적을 쓸 때마다 물린다. 문서화만으로는 부족하니 부호 결정 헬퍼를 같이 둔다.

### D2. 적용 대상

| 모듈 | 바꿀 것 |
|---|---|
| `measured_score` | `WORLD_UP`, `_axis_components`의 `world[2]`·`(world[0], world[1], 0)`, `_WorldFrame.up` 기본값 |
| `stroke_frame` | `stroke_basis`의 `WORLD_UP` 직교화, `FALLBACK_TANGENT`, "벽을 따라가는 수평축" |
| `motion_key` | `heading_word`, `body_placement`의 수평 성분 |
| `measured_pose` | `facing_yaw`, `MIN_FACING_HORIZONTAL` |

`measured_score`가 자체 `WORLD_UP`을 갖지 않고 `world_axes.UP`을 재수출한다.

### D3. 사전등록 상수는 움직이지 않는다

`CORRECTION_SIGMA_THRESHOLD = 2.0`, `MIN_CORRECTION_CM = 1.0`, `SIGMA_FLOOR_M = 0.02`,
`MAX_SIGMA = 6.0`, `GATE_RATIO = 0.5`, `DEFAULT_ERROR_M = 0.144`, `N_MIN = 20`,
`PAIR_SIGMA_FACTOR = sqrt(2)`, `DEFAULT_WEIGHTS`.

축이 바뀌면 이 임계들이 다른 분포를 만나지만, **그것이 재측정으로 알아내려는 것**이다.
결과를 본 뒤 임계를 옮기면 그 측정이 무의미해진다.

## 5. 메시 앵커 — 접촉점이 면 위인가

### 왜 넣는가

축 이름은 데이터 안에서 검증할 수 없다고 §2에 적었다. **메시가 그 예외를 만든다.** 착탄점이
레벨 메시 면 위에 놓이면, 월드 좌표 해석이 외부 기하와 맞아떨어진다는 증거가 된다. 일회성
스파이크가 아니라 **커밋된 검사**로 두면 앞으로 기하를 건드릴 때마다 앵커가 된다.

### 실측 결과 (레벨 1, 실제 착탄 1만 5천 점)

| | 선언된 변환 | **풀어낸 변환** |
|---|---|---|
| 최근접 삼각형 거리 중앙 | 3.68 m | **0.0 mm** |
| p95 | — | **0.0 mm** |
| 최대 | — | **8.46 mm** |
| UV 교차검증 R² | — | **0.99995 / 0.999999** |
| 분사각(수직에서) | — | 중앙 **29.8°** (p25 22.2 / p75 35.2 / p95 42.7) |

UV 교차검증은 거리 검사와 **독립적**이며, 2048×2048 아틀라스가 자연히 떨어져 나왔다 —
코드에 이미 있는 `motion_key.KeyParams(uv_size=2048.0)`와 같은 값이다.

레벨 10은 중앙 14 mm / p95 97 mm이고 UV R² 0.23~0.32, 분사각 중앙 84°(무작위에 가까움)로
**아직 신뢰할 수 없다.** 레벨 1만 앵커로 쓴다.

### D4. 변환은 **풀어낸 것**이지 선언된 것이 아니다

FBX가 선언한 노드 변환으로는 3.68 m 어긋난다 — 파일 어디에도 기록되지 않은 씬 수준 회전
(~90° yaw)이 빠져 있다. 맞는 변환은 Umeyama 유사변환 맞춤으로 **풀어낸** 것이다.
맞춘 스케일 0.0253981 대 선언값 유래 0.02540 (0.0074% 차이 — 선언값보다 **아래**다).

> **정정.** 앞선 판은 0.02568 / 1.1%를 적었다. 그 값은 `solve_alignment`의 이전 판에서 나온 것이고, 커밋된 아티팩트의 값은 위와 같다. 최종 리뷰가 이 불일치를 잡았다.

숫자만 박아 두면 출처를 잃는다. 그래서 둘 다 남긴다:

- `trainer/scripts/level_mesh.py` — 바이너리 FBX 7400 리더(표준 라이브러리 `struct`+`zlib`만)와
  정렬 맞춤. 맞춤을 **재현**할 수 있다.
- `trainer/data/level_alignment.json` — 맞춘 결과. 각 항목이 출처를 명시한다:

```json
{"level": 1,
 "provenance": "solved",
 "solved_transform": {"rotation": [9개], "translation": [3개], "scale": 0.0253981},
 "declared_scale": 0.02540,
 "fit": {"n_hits": ..., "median_mm": ~0, "p95_mm": ~0, "max_mm": 8.463, "uv_slope_u": ..., "uv_r2_u": ...},
 "source_fbx": "learning_mode_lv.1_rev.1.1.fbx"}
```

`"provenance": "solved"`가 필수 필드다. 선언된 변환을 쓰게 되는 날 `"declared"`가 되어야 하고,
그 구분이 사라지면 이 프로젝트가 반복해 맞은 결함("출처와 다른 라벨이 붙은 숫자")이 된다.

### D5. 허용치와 그 출처

**초안이 틀렸다. 거리 백분위는 이 앵커를 판정할 수 없다.**

초안은 "최근접 삼각형 거리가 p95 ≤ 10 mm, 최대 ≤ 100 mm"였다. Task 4 리뷰가 그것이 아무것도
판별하지 못함을 보였다:

- **착탄점 15,897개가 정확히 한 평면에 있다** — X 좌표의 서로 다른 float가 하나뿐이다.
  그래서 중앙값·p95가 **모든 후보에서** ~1e-7 mm다. 메시의 **틀린 면**에 붙은 적합까지 포함해서.
- `max_mm`은 외톨이 순서통계량이라 같은 적합을 다시 돌려도 크게 흔들린다
  (관측 0.64 ~ 35.0 mm).

즉 초안 관문의 두 조건 중 **판별력이 있는 쪽이 없다.** `p95`는 옳은 후보와 틀린 면 후보를
전혀 가르지 못하고(둘 다 ~1e-7 mm), `max`는 가를 때도 있지만 재실행마다 값이 달라져
**무엇을 통과시킬지 예측할 수 없다.** 안정적인 통계량은 판별력이 없고, 판별력이 있을 수도 있는
통계량은 안정적이지 않다.

> **정정.** 이 문서의 앞선 판은 "틀린 면 적합이 최대 17.7 mm로 초안의 관문을 통과한다"고
> 적었다. 그 값은 `solve_alignment`의 **이전 판**(B1/B2 개선 전)에서 나온 것이고, 현재
> 코드로 재현하면 틀린 면 후보의 최대가 ~130 mm로 나온다 — 그 값이라면 초안의
> `max ≤ 100 mm`에 오히려 걸린다. Task 5 구현자가 이 불일치를 자진 신고했다.
> **논거는 `p95`가 판별하지 못한다는 쪽으로 서야 하고**(그 부분은 두 판에서 동일하게
> 관측된다), `max` 하나로 세우면 안 된다.

모든 후보가 통과하는 관문은 관문이 아니다. 출처를 밝힌 사후 선택이었지만 **판별력 없는 지표를
정직하게 고른 것**이고, 출처를 밝히는 것과 판별하는 것은 다른 문제다.

**검사는 UV 일치로 한다.** 착탄점을 큰 면(전체의 94.8%)으로 제한하고, 메시에서 보간한 UV와
CSV의 `Ray Texture UV X/Y`를 회귀한다.

- **부호를 포함한** 기울기가 양 축 모두 기준값에서 **1% 이내**.
  기준값은 실측된 **−2048**이다(`level_mesh.EXPECTED_UV_SLOPE`).
- **R² ≥ 0.99** (양 축)

**부호를 빼면 안 된다.** `abs(slope)`로 재면 180° 뒤집힌 정렬이 그대로 통과한다.
실제로 적합에 그 모호성이 있었고 `abs(slope)`도 `R²`도 부호 불변이라 어느 검사도 보지 못했다.

**대칭은 하나가 아니라 최소 둘이다.** 이 문서의 앞선 판은 하나라고 적었고 그것은 틀렸다.

1. **패널 법선 축 180°** — 두 UV 기울기를 **함께** 뒤집는다.
2. **면내 축 180°** — **하나만** 뒤집어 부호가 섞인 쌍을 만든다. Umeyama의 자유도가 이것을
   같은 dominant-face 라벨로 재수렴시켜 살아남는다.

2번은 추정이 아니라 관측이다. 커밋 `ed71ce2`의 실제 회전을 히스토리에서 꺼내 현재 코드로
재평가하면 U −2047.54 / V **+**2047.79가 재현된다. 한때 이 값을 "오인용"으로 의심했으나,
그 판 시점의 진짜 기하를 정확히 읽은 것이었다.

선택 기준이 **부호를 모두 포함한** `(−2048, −2048)`과의 거리이므로 두 대칭을 함께 가른다
(승자가 7~8자릿수 차이로 이긴다). 부호를 하나라도 빼면 그 판별이 무너진다.

**부호 자체는 유도된 것이 아니다.** 선형 상관만으로 두 방향을 구별할 수 없다 —
구현자가 독립 유도를 시도했다가 그 논거가 "기울기가 양수인가"와 수학적으로 동일함(순환)을
스스로 증명했다. 그래서 `EXPECTED_UV_SLOPE`는 **적합이 일관되게 내는 분기를 고정한 값**이고
(15/15 시드), 뒤집힘을 보이게 하려고 박아 둔 것이다. 외부 실측이 반대 분기를 가리키면
이 상수는 움직인다. **인정된 분기 선택이지 측정인 척한 값이 아니다.**

**이 값도 측정을 본 뒤 정했다.** 다만 초안과 다른 점이 있다 — 실측 분리가 여섯 자릿수다.
옳은 후보가 R² 0.9999~1.0000, 틀린 면 후보가 0.000001~0.0038이다(옛 판별식에서는 13번째
유효숫자에서 동률이던 것들이다). 그 사이 어디에 선을 그어도 같은 판정이 나오므로 이 임계는
튜닝된 값이 아니라 **자연스러운 간극**이다. 거리 지표에는 그런 간극이 없었다.

교차검증이 독립적이라는 점도 중요하다. UV는 텍스처 좌표이고 거리는 기하이므로, 둘이 동시에
맞을 확률은 한쪽만 맞을 확률보다 훨씬 낮다. 그래서 앵커는 UV를 쓰되 거리도 **함께 기록**한다
— 판정에 쓰지 않고 기록만 한다.

이 검사는 목표를 판정하지 않고 **회귀를 잡는 용도**다. 사전등록이 필요한 것은 §6의 재측정이고,
그쪽 표집·시드는 이미 고정돼 있다.

## 6. 재빌드와 재측정

축이 바뀌면 동작 키가 96.5% 다른 버킷으로 가므로, **산포 아티팩트가 잘못된 버킷 위에 구워져
있다.** 다시 굽는다.

1. `build_spread_reference.py`로 전형기 아티팩트 재빌드. 층별 커버리지 표를 다시 낸다.
2. `improvement_study.py`를 **같은 사전등록 표집**(200쌍, 시드 `20260828`, 같은 선정 규칙)으로
   재실행.
3. 전후 비교표를 낸다. 비교 기준(축 수정 전, 다축 교정 적용 상태):

| 지표 | 수정 전 |
|---|---|
| `split` 중앙 / q3 / ≥0.70 | 0.0 / 0.158 / **3 of 149** |
| `same` 중앙 / ≥0.70 | 0.0 / 0 of 157 |
| 발동률(어떤 지시든) | 43.3% (68/157) |
| 천장(발동분) 중앙 / ≥0.70 가능 | 0.846 / 76.5% |
| 회수율 중앙 (same / split) | 0.294 / 0.329 |

결과를 본 뒤 유리한 절단이나 부분집합을 고르지 않는다.

## 8. 테스트

- `world_axes`의 각 연산이 유니티 규약을 낸다 — `vertical_of((1,2,3)) == 2` 류의 고정
- **규약이 실제로 지배하는지**: `UP_INDEX`를 바꿔치기하면 `_axis_components`·`stroke_basis`·
  `facing_yaw`·`motion_key`의 출력이 **전부** 따라 움직인다. 하나라도 안 움직이면 그 모듈이
  리터럴을 다시 박은 것이다
- **메시 앵커**: 레벨 1 착탄점을 큰 면으로 제한한 UV 회귀가 D5의 허용치 안
  (기울기 ±2048의 1% 이내, R² ≥ 0.99). 거리는 함께 기록하되 판정에 쓰지 않는다
- `level_alignment.json`의 모든 항목에 `provenance`가 있고 값이 `solved` 또는 `declared`
- FBX 리더가 알려진 작은 픽스처를 정확히 읽는다(정점 수·인덱스 수·UV 수)
- 회귀: 축 수정 후에도 `apply_measured`가 발부한 축만 옮긴다(다축 교정의 불변식)

성질을 보호한다고 이름 붙인 테스트는 **그 성질을 일부러 깨뜨려 실패를 확인한 뒤에만** 인정한다.
이 저장소에서 실패할 수 없는 단언이 지금까지 일곱 건 나왔다.

## 9. 열린 위험

- 축 수정으로 커버리지가 **나빠질 수 있다.** 버킷이 96.5% 재배치되므로 `n ≥ 20`을 채우는 키의
  구성이 완전히 달라진다. 그 방향은 측정 전에는 모른다
- 70% 판정이 어느 방향으로든 크게 움직일 수 있다. 좋아지면 이전 결론을, 나빠지면 이번 수정을
  의심하고 싶어지는데 **둘 다 하지 않는다** — 같은 표집으로 잰 두 값을 나란히 적는다
- 레벨 1이 정확히 평면(착탄 X가 7만 5천 프레임에서 비트 단위로 동일)이라 맞춤이 쉬웠다.
  다른 레벨은 그렇지 않을 수 있고, 앵커가 레벨 1에만 서 있다는 사실을 잊으면 안 된다
