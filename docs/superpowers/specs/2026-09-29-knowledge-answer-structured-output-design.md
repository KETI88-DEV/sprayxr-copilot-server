# knowledge_search 답변 구조화 출력 설계 (2026-09-29)

- 대상: `POST /api/v1/copilot/query`의 `task_type="knowledge_search"` 응답에서 `answer` 문자열과 `citations` 배열을 **구조적으로 보장**하는 설계
- 문제 제기: 지식 검색 답변이 정규화되어 있지 않음 → guided decoding 필요 여부 판단
- 선행: `docs/ai_copilot_v2_5_deployment_contract.md` §18.8, `docs/superpowers/plans/2026-09-17-v25-contract-migration.md`
- 범위 밖: 다른 4개 `task_type`(현재 `not_available`), 텔레메트리 5개 분석 인터페이스, 자세/시퀀스 설계(별도 문서 `2026-09-29-sprayxr-runtime-alignment-design.md`)
- 표기: 수치는 실측이며 표본을 밝힌다. 추정은 `[추정]`.

## 0. 설계 원칙

1. **JSON 봉투는 대상이 아니다.** `CopilotResponse`/`CopilotQueryData`는 서버가 Pydantic으로 직렬화한다. 모델은 봉투를 한 글자도 쓰지 않으므로 여기에 제약 생성을 걸 대상이 없다. 제약의 대상은 `answer` **문자열 내부**다.
2. **학습 분포를 떠나지 않는다.** v6.1 LoRA는 `[답변]`/`[근거]` 텍스트 스캐폴드로 SFT됐다. 같은 구조를 강제하는 문법을 쓰면 분포 이동이 거의 없다. JSON으로 바꾸면 이동이 크다(§3.1).
3. **사후 필터보다 디코드 시점 차단을 우선한다.** 다만 요청마다 문법을 다시 컴파일해야 하는 차단은 지연이 측정되기 전까지 채택하지 않는다. 지연은 이미 제품 지적사항이다.
4. **정규화 함수는 전역 함수(total function)여야 한다.** 파싱 실패를 원문 통과로 처리하면, 정규화가 필요한 경우에 정확히 아무 일도 하지 않는다.
5. **`citations`는 "검색한 것"이 아니라 "근거로 쓴 것"이다.** 두 집합을 한 필드에 섞지 않는다.

## 3. 설계

### 3.1 제약 방식: JSON이 아니라 학습된 텍스트 형태

**2026-09-29 Spark 실측으로 확정했다.** vLLM 0.29.0에서 제약은 채팅 요청의 `structured_outputs`로 전달되고, 그 안의 `regex`와 `grammar` 두 키가 모두 동작한다. 우리는 `regex`를 쓴다.

| | JSON 스키마 | 텍스트 제약 (채택) |
|---|---|---|
| v6.1 SFT 분포와의 거리 | **큼** — 학습 타깃은 `[답변]`/`[근거]` 평문이었고 JSON 이스케이프·중괄호는 학습되지 않았다 | **거의 없음** — 학습 타깃의 형태를 그대로 패턴으로 옮긴다 |
| 방언 위험 | 없음 | `grammar` 키는 GBNF를 받지만 `Grammar` 스키마의 `syntax` enum은 `lark`/`regex`다. **`regex`를 쓰면 이 모호함이 사라진다** |
| 파싱 | `json.loads` | 패턴이 보장하므로 §3.4의 분해가 전역 함수가 된다 |

### 3.2 패턴 정의

```python
_BODY_LINE = r"[^\n\[]+"
_DOC_ID    = r"DOC-[A-Za-z0-9_-]+-C[0-9][0-9][0-9][0-9]"

ANSWER_REGEX_NO_EVIDENCE   = rf"\[답변\] {_BODY_LINE}(\n{_BODY_LINE})*"
ANSWER_REGEX_WITH_EVIDENCE = ANSWER_REGEX_NO_EVIDENCE + rf"(\n\[근거\] {_DOC_ID}(, {_DOC_ID}){{0,2}})?"
```

설계 귀결:

- `[근거]`가 **최대 1회**다(§1.1의 23건이 구조적으로 불가능해진다).
- `[판정]`·`[원인]`·`[조치]`가 나올 수 없다. 패스트 경로가 측정값 없는 판정을 발행하는 것을 프롬프트가 아니라 패턴이 막는다.
- 증거가 없으면 패턴에 `DOC` 절이 아예 없으므로 **문서를 주지 않은 요청이 출처를 제시할 수 없다.**
- 본문이 `[`를 **어디에도** 쓸 수 없다. 줄머리만 막는 초안으로는 부족했다 — 제약 없는 프로브가 `[답변] …합니다. [분석] 이 답변은…`처럼 **같은 줄에** 자평 절을 이어 붙였다. 대가로 본문의 정당한 대괄호 표기도 못 쓰지만, 관측된 누출을 확실히 막는 쪽을 택했다.
- 본문 줄은 `[`로 시작할 수 없고 증거 줄은 `[`로 시작하므로, 개행 뒤 분기가 모호하지 않다.

패턴은 정적이므로 프로세스 기동 시 상수로 들고 있고 요청당 조립 비용이 없다.


### 3.3 인용 소속 검사 (D3)

문법은 id의 *형태*만 보장한다. 소속은 서버가 판단한다.

```
cited        = 문법이 보장한 [근거] 파싱 결과 (0..3개, 순서 유지)
retrieved    = 이번 요청의 rerank 히트 chunk_id 집합 (|retrieved| ≤ 8)
validated    = [c for c in cited if c in retrieved]      # 순서 유지, 중복 제거
dropped      = [c for c in cited if c not in retrieved]
```

- `dropped`가 비어 있지 않으면 **요청당 WARNING 1건**으로 `request_id`, `dropped`, `|retrieved|`를 남긴다. 이 비율이 §1.2의 10.0%에 대한 라이브 관측치가 된다.
- `validated`가 비었고 `retrieved`가 비어 있지 않으면 → 답변은 그대로 두고 `citations=[]`로 응답한다. 답변을 버리지 않는다. 근거 없는 답변임을 `citations`의 공집합이 이미 표현한다.
- `answer` 문자열의 `[근거]` 줄은 **서버가 `validated`로 다시 렌더한다.** 본문과 배열이 불일치할 수 없다.
- `retrieved`가 비어 있으면(`use_rag="N"` 또는 히트 0) `[근거]` 줄을 붙이지 않는다.

**선택 사항(측정 후 결정):** `cite`를 `retrieved`의 8개 id 열거로 바꾸면 증거 밖 인용이 디코드 시점에 불가능해진다. 대가는 요청당 문법 컴파일이다. 원칙 3에 따라 **컴파일 p95가 30ms 미만으로 측정될 때만** 채택한다. 측정 없이는 채택하지 않는다.

### 3.4 정규화 함수의 전역화 (D1)

구현 시 추가로 확정한 두 가지:

- **머리말은 버리지 않고 본문 앞에 붙인다.** 첫 헤딩보다 앞선 산문을 헤딩 없는 경로로 보내면 답변 본문 안에 `[분석]` 마커가 중첩되어 SIM의 파싱을 깨뜨린다. `_split_with_preamble`이 머리말과 섹션을 함께 돌려준다.
- **답변 섹션이 하나도 없으면 발행하지 않는다.** `판정|원인|조치|근거`만 온 경우(코퍼스 1건) 판정문을 답변으로 내보내면 측정값 없는 판정을 발행하는 것이다. `답변을 생성하지 못했습니다.`를 반환하고 `repair_path="no_answer_section"`으로 기록한다. 문서 커버리지에 대한 거짓 주장("문서에 정보가 없습니다")을 하지 않기 위해 우리 쪽 실패로 표현한다.
- **산문을 다시 쓰지는 않는다.** 드롭된 id를 본문에서 제거하고 남은 구분자(빈 괄호, 중복 쉼표, 괄호 안쪽 공백)만 정돈한다. `SENTINEL(DOC-x 참조)` → `SENTINEL(참조)`.

`normalize_fast_knowledge_response`를 대체한다. 새 함수는 반드시 `(answer, citations, diagnostics)`를 반환하며 **원문 통과 분기를 갖지 않는다.**

```
parse_knowledge_answer(raw, retrieved) -> KnowledgeAnswer
  1. 문법 보장 경로: [답변]/[근거]로 분해. 성공 → validated 렌더.
  2. 문법 미적용/실패 경로(structured_output: off, 또는 문법 지원 없는 서버):
     2a. 섹션 분해 성공 → [답변]|[분석]을 본문으로, [판정]/[원인]/[조치] 폐기,
         [근거] 중복은 병합, 본문의 DOC id는 제거하고 validated로 재렌더
     2b. 섹션 분해 실패 → 전체를 본문으로 보고 "[답변] " 접두를 붙인다.
         본문의 DOC id는 제거한다.
  3. 어떤 경로든 반환값은 정확히 "[답변] ...(\n[근거] ...)?" 형태다.
  4. 2a/2b로 내려간 건수는 diagnostics.repair_path에 기록하고 WARNING으로 남긴다.
```

2b가 있기 때문에 이 함수는 어떤 입력에도 계약 형태를 반환한다. **정규화 실패는 이제 존재하지 않고, 대신 복구 경로 통계가 남는다.**

### 3.5 설정 스위치와 폴백

```yaml
llm:
  structured_output: "off"        # "on" | "off". YAML이 off를 false로 읽으므로 인용한다
  structured_output_fallback: true # 서버가 제약을 거부(400)하면 제약 없이 1회 재시도
```

- **`grammar`와 `json`은 폐기값이며 설정하면 기동이 `ValueError`로 실패한다.** 둘 다 이 배포가 쓰지 않는 전달 방식을 가리킨다. 조용히 `on`으로 매핑하지 않는다 — 옛 초안대로 쓴 설정은 고쳐야 할 것이지 추측할 것이 아니다.
- **제약은 `openai` 백엔드에서만 적용된다.** 인프로세스 HF 모델은 자체 logits processor가 필요하고, HF는 학습·평가용 백엔드로 남는다(AGENTS.md). `hf`에서는 `_answer_regex`가 `None`을 반환한다.
- 거부를 한 번 학습하면 프로세스 수준에서 기억해 매 요청 400을 물지 않는다.
- `off`는 §3.4의 복구 경로만 쓴다. 지금 동작보다 엄격하되 제약 없이 돈다.

### 3.6 vLLM 배선 — 실측으로 확정

`OpenAIBackend.build_payload`에 선택적 필드를 더한다. 기존 키는 건드리지 않으므로 제약 없는 요청은 이전과 바이트 동일하다.

```python
if answer_regex:
    payload["structured_outputs"] = {"regex": answer_regex}
```

| `structured_outputs: {"regex": "SENTINEL-[0-9][0-9][0-9]-END"}` | 200, 출력이 정확히 `SENTINEL-102-END` — **제약이 실제로 걸린다** |
| `structured_outputs: {"grammar": "<GBNF>"}` | 200, 같은 SENTINEL 출력 — GBNF도 받지만 방언 위험이 있어 쓰지 않는다 |
| `structured_outputs: {"grammar": {"definition": …, "syntax": "regex", …}}` | **400** — `grammar`는 문자열이어야 한다. `Grammar` 객체 스키마는 다른 필드 것이다 |
| 최상위 `guided_grammar` | **200인데 무시된다** — 응답이 제약을 따르지 않는다 |
| `extra_body: {"guided_grammar": …}` | **200인데 무시된다** — `extra_body`는 OpenAI 파이썬 클라이언트 개념이고, 생 HTTP에서는 서버가 모르는 키다 |
| `guided_decoding_backend` | `ChatCompletionRequest`의 필드가 아니다(배치 변형에만 있다). 보내지 않는다 |

**시험 설계에서 배운 것.** 첫 프로브는 "응답이 `[답변] `로 시작하는가"로 판정했는데, v6.1은 제약이 없어도 그렇게 시작하도록 SFT됐다. **실패할 수 없는 시험이었다.** 모델이 스스로 낼 이유가 없는 SENTINEL을 강제하고 나서야 판정이 섰다. 200은 제약이 걸렸다는 증거가 아니다 — 이 서버는 모르는 필드를 거부하지 않는다.

그 결과 `StructuredOutputUnsupportedError`(400 폴백)로는 **무시되는 경우를 잡을 수 없다.** 필드명이 추측이 아니라 측정으로 고정되어야 하는 이유다.

**나머지 확인 항목(토크나이저만으로 해소).**

- `[답변]`·`[근거]` 다중바이트 리터럴의 토큰 경계 충돌 **없음**. 서빙 번들 토크나이저(vocab 248,044)에서 `답`=152065, `변`=151315, `근`=150858, `거`=89011로 각 글자가 완결된 단일 토큰이고, `[답변] `은 `[58, 152065, 151315, 60, 220]`의 정확한 토큰 열이다. `DOC-doc_0086-C0001`도 `DOC`/`-doc`/`_`/숫자 개별 토큰으로 쪼개져 자릿수 규칙과 1:1 대응한다.
- `enable_thinking=false`와 **안전하게 병용된다.** 템플릿이 생성 프롬프트 말미에 닫힌 빈 블록 `<think>\n\n</think>\n\n`을 미리 박으므로 생성은 답변 첫 토큰부터 시작한다. `enable_thinking=True`에서는 프롬프트가 열린 `<think>\n`으로 끝나 같은 패턴이 템플릿이 초대한 추론을 금지하므로, `_generate_direct`가 thinking이 켜지면 제약을 버리고 경고한다.
- `repetition_penalty=1.15`는 제약이 토큰을 1개로 강제하는 구간에서 무력하고 자유 본문 구간에서만 작용한다. 본문 품질 영향은 §5가 잰다.
- **컴파일 비용은 아직 분리하지 못했다.** 관측치는 SENTINEL 2,679ms / 2,863ms, 계약 패턴 10,727ms인데 차이가 생성 토큰 수(약 10 vs 약 60)에 지배된다. `max_tokens=8`로 같은 패턴을 연속 호출해야 제대로 잡힌다. §3.3의 동적 패턴(증거 id 열거) 채택 여부는 이 측정 없이 결정하지 않는다.


### 3.7 왜 개발 호스트에 vLLM 서버가 없는가

- AGENTS.md가 vLLM을 **필수 의존성으로 만들지 못하게** 한다. `ship-paint-trainer`에 `vllm` 모듈이 없다(실측: `ModuleNotFoundError`). 학습·평가 기본 백엔드는 HF NF4다.
- `deploy/docker-compose.yml`에는 vllm 서비스 정의가 **아예 없다.** 유일한 정의는 `deploy/spark/compose.yaml`이고 `platform: linux/arm64` — aarch64/GB10 전용이라 이 x86 호스트에서 실행되지 않는다.
- 즉 `backend: openai` 경로는 Spark를 위해 만들어졌고 거기서 검증됐다. 개발 호스트의 다른 vLLM 버전에서 나온 항목 1의 답은 **정본이 아니고 전이되지 않는다.**
- 하드웨어는 있다: A40 44.3 GiB(실측, 현재 0 MiB 사용), FP8 번들 29G도 이 호스트에 있다. BF16 52G는 들어가지 않는다. 다만 A40은 Ampere(SM 8.6)이므로 FP8 block-128 서빙 지원과 `Qwen3_5ForConditionalGeneration`(Gated DeltaNet 하이브리드·MTP·비전 타워) 지원이 x86 빌드에서 보장되지 않는다. 이 두 위험 때문에 개발용 vLLM 기동은 항목 1의 답을 얻는 수단으로는 비싸고 불확실하다.

## 5. 품질 게이트

게이트는 `trainer/scripts/run_rag_eval.py`(50문항, `/data/eval/eval_set.jsonl`)를 쓴다. 이 평가 세트는 문항마다 `required_chunks`를 갖고 있어 **인용 정확도를 직접 잴 수 있다.** 현재 `run_rag_eval.py`는 이 지표를 계산하지 않으므로 추가한다.

| 지표 | 성격 | 기준 |
|---|---|---|
| `manual_score` (5축 평균, `run_rag_eval.py:232`) | 단계형 통계 게이트 | Welch 95% CI, Δ=0.2. CI 하한 > −Δ면 통과, 상한 < −Δ면 실패, 그 외 8→18회 확장. FP8 때와 같은 절차. **예상 상쇄 −0.040은 품질 저하가 아니다**(아래) |
| `rouge_l`, `bertscore_f1` | 참고 | 보고만 |
| **구조 준수율** | 경성 게이트 | `off` 경로에서도 100%. 문법 경로에서 100% 미만이면 배선 결함이다 |
| **증거 밖 인용률** | 경성 게이트 | 0%. §1.2의 10.0%가 0으로 가는 것이 이 작업의 정의다 |
| **인용 재현율** (`validated ∩ required_chunks`) | 신설·보고 | 기준선 먼저 측정. 축소된 `citations`가 정답 청크를 놓치는지 본다 |
| p50/p90 지연 | 경성 게이트 | 기준선 대비 +5% 이내. 문법 마스크는 디코드 시점 비용이므로 [추정] 무시 가능하지만 측정으로 확인한다 |
| `completeness`(길이비 0.5~3.0, `run_rag_eval.py:223`) | 감시 | 문법이 본문을 짧게 만들면 이 축이 먼저 떨어진다. 하락 시 `body` 상한(600자)을 조정한다 |

**게이트 해석에 필요한 보정 하나.** `run_rag_eval.py:206-214`의 `faithfulness` 축은 `len(citations) >= 1`만 요구하므로 8개를 1~3개로 좁히는 것 자체는 점수를 바꾸지 않는다. 그러나 §1.3의 전부/전무 성질 때문에 증거 밖 인용 건(10.0%)은 `validated`가 **공집합**이 되어 `faith_score`가 2→0으로 떨어진다. 이는 `manual_score`에 **−0.040**의 결정론적 상쇄를 만든다(0.100 × 0.4).

이 −0.040은 올바른 필터링의 결과이며 품질 저하가 아니다. Δ=0.2가 이를 흡수하지만, **문법 경로의 하락으로 오독하지 않도록 보고서에 분리해 싣는다.** 비교는 `off`(수정 후) vs `grammar`(수정 후)로 하고, 수정 전 기준선은 별도 열로만 보여준다.

측정 시 같은 컨테이너에서 다른 CPU 부하를 돌리지 않는다(과거 100.2s vs 42s 오염 사례).

| 지연 p50 | 22,556ms | 22,414ms | — |
| 지연 평균 | 23,517ms | 22,319ms | — |

**전제 6 해소.** `use_rag=N` 두 건이 `on`에서 2줄 본문을 내고 계약 검사를 통과했다. 패턴의 `(\n[^\n\[]+)*` 부분이 실물에서 동작한다.

**지연 차이는 유의하지 않다.** 평균 +1,198ms(+5.4%)지만 표준오차가 2,349ms로 95% 구간이 [−3,406, +5,801]ms이고 0을 포함한다. p50은 +0.6%다. p90의 +16.7%는 10표본의 최댓값 **한 관측**이므로 근거가 아니다.

**그러나 `off`의 10/10이 "제약이 불필요하다"를 뜻하지 않는다.** 0/10의 95% 상한은 rule of three로 **30%**다. §1.1이 잰 무도구 부분집합 이탈률 **16.9%(25/148)**가 참이어도 10건에서 0건이 나올 확률이 **15.7%**다. 이 스모크는 심한 파손을 배제했을 뿐 10~20%대 꼬리를 배제하지 못한다.

### 11.2 S5의 목적이 바뀌었다

애초 질문은 "제약이 품질을 떨어뜨리는가"였다. S4가 양쪽 동률을 냈으므로 이제 결정적인 질문은 **"패스트 경로가 제약을 필요로 할 만큼 이탈하는가"**다. 순서를 바꾼다.

1. **`off` 단독으로 먼저 돌린다.** 50문항 × 8회 = 400표본에서 `contract_shaped`를 센다. 400건 전부 통과면 참 이탈률의 95% 상한이 0.75%이고, 그러면 제약은 지연 위험만 더하므로 **`off`가 기본값**이다. 코드는 남겨 둔다 — 패스트 프롬프트나 어댑터가 바뀌어 이탈이 돌아오면 스위치 하나로 켠다.
2. **`off`에서 이탈이 잡힐 때만 `on` 팔을 돌린다.** 그때 §5의 Welch Δ=0.2 비교가 의미를 갖는다.

비용이 절반이 되고, 답을 못 얻는 조건을 돌리지 않는다.

### 11.3 이번 측정이 드러낸 더 큰 문제: 지연

**p50 22.4초, 최대 36.0초다.** 이 프로젝트가 처음부터 지적받은 항목이고, 제약과 무관하게 양쪽 조건에서 같다.

**왜 BF16이 도는가 — 결정이 아니라 미확인이다.** 계획 D1은 Spark 서빙 산출물을 FP8로 정했고 BF16은 마스터·폴백으로 뒀다. 그런데 `deploy/spark/README.md` §19 미확인 항목 1이 **"GB10(SM121)에서 Qwen3.6 FP8 block-128 로드와 커널 동작"**을 미확인으로 남겨 두었다. 즉 FP8을 포기한 결정이 있었던 게 아니라, **검증되지 않은 경로였기 때문에 확실한 BF16이 올라간 것**이다. 이 문서의 이전 판이 이를 "롤백"이라 적은 것은 부정확했다.

그 결과로 딸려온 것이 하나 더 있다. README §18의 BF16 절차 4단계가 `ENABLE_MTP=0`을 명시하므로, **MTP 추론적 디코딩도 함께 꺼져 있다**(`deploy/spark/vllm/entrypoint.sh:28`, 기본값 0).

**지렛대는 둘이고 성질이 다르다.**

| | 기대 효과 | 대가 | 막고 있는 것 |
|---|---|---|---|
| MTP 추론적 디코딩 | D1 주석이 "둘 다 MTP로 추가 이득" [추정] | **없음 — 출력이 정확히 같다.** 초안을 본 모델이 검증한다 | §19-2: `--language-model-only`와 동시 사용 미확인. `.env` 한 줄로 시험 가능 |
| FP8 | D1 사전 추정 **BF16 약 5.3 tok/s → FP8 약 10 tok/s**(273GB/s 기준). 가중치 55.6GB → 30.9GB, **1.80배** | 층 출력 상대오차 **2.65%** 실측(NF4 9.2%의 약 0.29배). 품질 게이트 필요 | §19-1: GB10에서 로드·커널 동작 미확인. 번들은 A40에 있고 `verify` 통과 |

**관측이 D1의 추정과 맞는다.** 5.3 tok/s면 22초 동안 약 117토큰인데, 2~5문장 한국어 답변의 길이대와 겹친다(프리필·RAG 시간을 빼면 실제 출력은 그보다 적다). 즉 지금 지연은 BF16 디코드가 지배한다는 가설과 모순되지 않는다. 다만 이는 정황이고, 아래 측정이 직접 가른다.

### 11.4 22초의 분해 — 디코드가 전부다 (2026-09-29 실측)

같은 24토큰 프롬프트를 `max_tokens`만 바꿔 vLLM에 직접 던졌다. 조건당 2회, 재현성은 79ms·108ms로 매우 좋다.

| `max_tokens` | 시간 | 출력 |
|---|---|---|
| 16 | 3,543 / 3,622ms | 16토큰 |
| 256 | 56,078 / 56,186ms | 256토큰 |

- 추가 240토큰에 **52,550ms** → 토큰당 **219.0ms = 4.57 tok/s**
- 고정 비용(프리필 24토큰 + 네트워크 + 스케줄링) **79ms** — 사실상 없다
- D1의 사전 추정 BF16 5.3 tok/s 대비 실측이 **86%**다. 추정이 맞았다

스모크 p50 22,414ms를 이 속도로 환산하면 출력 **약 102토큰**이고, 디코드가 총시간의 **99.6%**다. (이 환산은 RAG 프롬프트의 프리필도 무시할 만하다고 가정한다. 실제 프리필이 수백 ms~2초여도 디코드 비중은 90%를 넘는다.)

**두 지렛대가 정확히 지배적 비용을 겨냥한다.**

| 수단 | 배수 | 22.4초 → | 성질 |
|---|---|---|---|
| MTP 1토큰 | 1.4배 **[가정]** — 수용률 미측정 | 16.0초 | 무손실 |
| FP8 | 1.80배 (총 가중치 55.6→30.9GB 기준) | 12.5초 | 오차 2.65%, 게이트 필요 |
| 둘 다 | 2.52배 | 8.9초 | |

FP8 배수의 단서: 1.80은 번들 총량 비율이다. 텍스트 디코드는 비전 타워(BF16 유지)를 읽지 않으므로 실제 작업집합 비율은 이와 다를 수 있다. MTP 1.4배는 **측정값이 아니라 가정**이며, 수용률에 따라 1.0~2.0 사이다.

**출력 길이 자체도 지렛대다.** 102토큰 × 219ms가 곧 22초다. `ROUTE_MAX_TOKENS["fast"]=256`은 걸리지 않으므로, 답변을 짧게 만들면 비례해서 줄어든다. 다만 계약의 "2~5문장"을 줄이는 것은 품질 결정이다.

**인지 지연은 별개다.** `run_streaming()`은 완성된 답을 다시 쪼갤 뿐 토큰 스트리밍이 아니다(AGENTS.md). 실제 토큰 스트리밍을 붙이면 총시간은 그대로여도 첫 글자가 1초 안에 나온다. `/api/v1/copilot/query`는 비스트리밍 계약이라 해당되지 않고, 채팅 SSE 경로에만 해당한다.

**게이트 해석 주의:** §5 말미의 −0.040 상쇄는 인용 필터링의 결정론적 결과다. 비교는 `off`(이번 수정 후) vs `on`(이번 수정 후)로 하고, 수정 전 수치를 기준선으로 쓰면 제약 탓이 아닌 하락을 제약에 돌린다.
